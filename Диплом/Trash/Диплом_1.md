# ВВЕДЕНИЕ {#введение}

Актуальность темы. В последние годы область генеративного искусственного интеллекта (Generative AI) демонстрирует экспоненциальный рост. Достижения в сфере больших языковых моделей (LLM) и диффузионных моделей кардинально меняют подходы к созданию контента. Однако, несмотря на доступность мощных инструментов, их применение в сфере сторителлинга сталкивается с фундаментальной проблемой: повествование, в своей сущности, является не просто линейной последовательностью текста, а сложной, многомерной, нелинейной структурой. Сюжетные линии ветвятся и пересекаются, персонажи вступают в сложные взаимоотношения, а целостность истории зависит от множества факторов.

Существующие ИИ-инструменты зачастую работают изолированно, а их архитектура не приспособлена для управления сложным нарративным графом. Это приводит к потере контекста, нарушению причинно-следственных связей и невозможности эффективной работы с ветвящимися сценариями. Разработка платформы, которая не просто генерирует контент, а предоставляет инструменты для структурирования и управления сложным повествованием, является актуальной и востребованной задачей, способной вывести процесс создания историй на качественно новый уровень.

Объектом исследования является процесс создания, управления и автоматизированной догенерации сложного, нелинейного, мультимедийного повествовательного контента с использованием технологий генеративного искусственного интеллекта.

Предметом исследования выступают архитектурные решения, модели данных и программные средства, обеспечивающие производительность, надежность и консистентность интеллектуальной платформы. В частности, предметом исследования являются:

1. Графовые модели данных для представления нелинейных сюжетных структур.  
2. Асинхронные, распределенные архитектуры для выполнения ресурсоемких операций без блокировки пользовательского интерфейса.  
3. Паттерны управления состоянием на стороне клиента (нормализованный кэш, очередь действий) для обеспечения отзывчивости и целостности данных.  
4. Механизмы координации и обмена данными между компонентами системы (API, Pub/Sub, WebSockets).

Целью работы является разработка и реализация высокопроизводительной интерактивной веб\-платформы для создания и управления сложными, нелинейными повествованиями, использующей генеративный ИИ для достраивания и обогащения контента.

Для достижения поставленной цели необходимо решить следующие задачи:

1. Провести анализ существующих подходов и выявить архитектурные проблемы, возникающие при попытке смоделировать нелинейный нарратив с помощью реляционных баз данных и синхронных вычислений.  
2. Спроектировать масштабируемую, асинхронную архитектуру, включающую API-шлюз (Orchestrator), асинхронный обработчик задач (Worker) и систему уведомлений в реальном времени.  
3. Разработать графовую модель данных, способную эффективно представлять иерархию и последовательность сюжета, включая точки ветвления и слияния (BranchSet).  
4. Реализовать производительный пользовательский веб\-интерфейс с визуальным конструктором структуры истории, применив продвинутые паттерны управления состоянием для обеспечения его отзывчивости и надежности.  
5. Провести тестирование прототипа, оценив эффективность предложенных архитектурных решений в решении проблем производительности, целостности данных и качества пользовательского опыта.

Научная новизна работы заключается в следующем:

1. Формализован подход к моделированию нелинейного повествования с помощью графовой модели, включающей специализированный мета-узел BranchSet для явного определения точек ветвления, что радикально упрощает логику навигации и визуализации.  
2. Разработана и применена гибридная модель "очереди действий" (Action Queue) на стороне клиента, которая обеспечивает транзакционную целостность пользовательских сессий в асинхронной среде, что является прагматичным и надежным решением для систем с дорогими, зависимыми от состояния операциями.  
3. Спроектирован и описан эффективный протокол взаимодействия "умного" бэкенда и "ленивого" фронтенда через "обогащенный" API (GET /api/context), инкапсулирующий сложность обхода графа на сервере.

Практическая значимость исследования состоит в создании архитектурного прецедента для разработки нового класса инструментов для авторов. Платформа может быть использована в игровой индустрии для проектирования квестовых цепочек, в киноиндустрии для оперативной подготовки вариативных сторибордов, в образовании для создания интерактивных обучающих материалов, а также в любой сфере, где требуется работа со сложными, ветвящимися сценариями.

Методы исследования. В работе использовались методы системного анализа, проектирования распределенных систем, теории графов для моделирования данных, а также архитектурные паттерны (Pub/Sub, CQRS-like Action Queue, Normalized Cache). Для реализации генеративных функций применялись большие языковые модели.

Апробация результатов. Основные положения и результаты работы реализованы в виде программного прототипа веб\-платформы, ключевые архитектурные решения и их обоснование задокументированы, а исходный код размещен в открытом репозитории.

# 1 АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ И ТЕХНОЛОГИЙ ГЕНЕРАТИВНОГО ИИ {#1-анализ-предметной-области-и-технологий-генеративного-ии}

### 1.1 Традиционные методы и программные средства создания графических повествований {#1.1-традиционные-методы-и-программные-средства-создания-графических-повествований}

Процесс создания комиксов и сторибордов исторически является мультидисциплинарным, требующим совмещения навыков сценариста, раскадровщика, художника-постановщика и колориста. Традиционный цикл производства включает в себя следующие этапы:

1. Написание сценария: Формирование текстовой основы с описанием диалогов и действий.

2. Эскизирование (Layout): Создание первичных набросков для определения композиции кадра.

3. Контуровка и покраска: Детализация изображений и работа с цветом.

Работа над текстовой составляющей повествования сегодня выходит за рамки обычных текстовых редакторов. Профессиональные инструменты делятся на две категории:

1. Инструменты для драматургического структурирования и написания сценариев:

   * Final Draft / Kit Scenarist: Отраслевые стандарты для кино и телевидения.

     * *Преимущества:* Автоматическое форматирование под «голливудский стандарт» (интервалы, шрифты, блоки диалогов). Это позволяет сценаристу не отвлекаться на верстку.

     * *Функциональность:* Наличие инструментов для карточного планирования (Index Cards), где каждая сцена — это отдельная сущность, которую можно перемещать по сюжетной линии.

   * Celtx: Облачное решение, которое позволяет не только писать текст, но и сразу готовить раскадровку (в ручном режиме) и производственные сметы.

2. Инструменты для организации сложных миров и нарратива (для писателей):

   * Scrivener: Мощная среда для работы с длинными текстами (романы, лонгриды).

     * *Преимущества:* Система «метаданных». Писатель может хранить в одном проекте черновики, досье персонажей, фотографии-референсы и заметки по миру.

     * *Функциональность:* Режим нелинейного письма — возможность работать над разными главами параллельно и легко менять их местами.

   * Notion / Obsidian: Современные системы управления знаниями (Zettelkasten), которые часто используются для создания «Библии проекта» (описания лора, связей между героями и временных шкал).

Несмотря на удобство структурирования мыслей, у всех этих систем есть общие ограничения, которые решает твоя платформа:

1. Разрыв между текстом и визуалом: Ни одна из перечисленных программ не способна «понять» написанный текст и предложить его визуальное воплощение. Переход от сценария к раскадровке остается полностью ручным и требует участия художника.

2. Отсутствие генеративной помощи: Эти инструменты работают как хранилища и редакторы, но они не помогают автору, когда тот сталкивается с логическими тупиками в сюжете или нехваткой идей для диалогов.

На рынке доминируют профессиональные графические редакторы и специализированное ПО:

1. Adobe Photoshop / Clip Studio Paint: Мощные инструменты для рисования, обладающие широким набором кистей и функций для работы с растрами.

   * *Преимущества:* Полный контроль над каждой деталью, возможность передачи сложных эмоций и уникального авторского стиля.

2. Storyboard Pro / Final Draft: Инструменты для структурирования сценариев и создания базовых раскадровок.

   * *Преимущества:* Удобство работы с таймлайном и текстом, интеграция с пайплайнами кинопроизводства.

Несмотря на функциональность, данные сервисы обладают существенными недостатками для современного темпа медиапроизводства:

1. Высокий порог вхождения: Требуются годы обучения академическому рисунку и композиции.

2. Ресурсная емкость: Создание качественного прототипа контента требует значительных временных затрат и высокой стоимости привлечения специалистов.

3. Отсутствие интеллектуальной поддержки: Программы являются лишь «цифровым холстом», они не способны предложить варианты развития сюжета или преодолеть «творческий блок» автора.

   ### 1.2 Обзор технологий генеративного ИИ в контексте мультимедийного контента {#1.2-обзор-технологий-генеративного-ии-в-контексте-мультимедийного-контента}

Развитие технологий генеративного ИИ открывает возможности для автоматизации рутинных этапов, описанных выше. В рамках данной работы выделяются три ключевых технологических стека:

1. Большие языковые модели (LLM) для генерации повествования. Использование моделей, таких как GPT-4, Llama-3 или Mistral, позволяет автоматизировать создание связных сюжетов и диалогов.  
   * Функция: Преобразование краткой идеи пользователя в детализированный сценарий с разбивкой по кадрам.  
   * Преимущество: Возможность генерации множества вариаций сюжета за секунды, что критически важно для этапа превизуализации.  
2. Диффузионные модели для синтеза изображений. Модели семейства Stable Diffusion и DALL-E 3 обеспечивают генерацию высококачественных иллюстраций на основе текстовых промптов.  
   * Особенность: Возможность использования механизмов LoRA и Dreambooth для обучения системы конкретному художественному стилю.  
   * Роль: Быстрая визуализация концепций, которая в традиционном подходе занимала бы часы работы художника.

   ### 1.3. Проблема связности и координации при сквозной генерации {#1.3.-проблема-связности-и-координации-при-сквозной-генерации}

Основным барьером при использовании ИИ для создания комиксов является проблема «взаимосвязанности» (consistency). При независимой генерации кадров персонажи и окружение могут терять свои характерные черты.

Существующие подходы к решению:

1. ControlNet: Технология, позволяющая управлять композицией и позами персонажей, обеспечивая их стабильность от кадра к кадру.

2. IP-Adapter: Метод поддержания визуального сходства объектов без полного переобучения модели.

3. Агентные модели и FSM: Использование конечных автоматов для координации взаимодействия между текстовым и визуальным модулями.

Стоит сделать акцент на следующих выводах:

1. Разрыв между инструментами: Существующее ПО либо отлично работает с графикой, либо с текстом, но не обеспечивает их бесшовную интеграцию. Твоя платформа закрывает этот «пробел».

2. Демократизация творчества: В то время как традиционные редакторы требуют многолетнего обучения, использование генеративного ИИ позволяет создавать качественные прототипы (MVP) людям без художественного образования.

3. Экономическая эффективность: Переход от ручного рисования к генеративному позволяет в разы сократить цикл предпроизводства (pre-production), что критически важно для маркетинга, образования и инди-геймдева.

# 2 ПРОЕКТИРОВАНИЕ АРХИТЕКТУРЫ ПЛАТФОРМЫ {#2-проектирование-архитектуры-платформы}

## 2.1 Требования к интеллектуальной веб\-платформе {#2.1-требования-к-интеллектуальной-веб-платформе}

На этапе проектирования системы были определены ключевые функциональные и нефункциональные требования, обеспечивающие решение задач сквозной генерации контента и поддержания нелинейности повествования.

К основным функциональным требованиям относятся: 

1. создание и иерархическое структурирование проектов по схеме: «История» (Story) – «Арка» (Arc) – «Глава» (Chapter) – «Сцена» (Scene)  – «Кадр» (Frame);   
2. поддержка механизмов ветвления сюжета на любом уровне иерархии;  
3. автоматизированная генерация текстовых сценариев и описаний кадров на основе контекста с использованием больших языковых моделей (LLM);  
4. предоставление функционала интеллектуального достраивания фрагментов истории по запросу пользователя; — асинхронное выполнение ресурсоемких задач генерации.

Нефункциональные требования включают: 

1. обеспечение логической связности (консистентности) сюжета при нелинейном развитии событий;   
2. минимизация задержек интерфейса при взаимодействии с внешними ИИ-сервисами;   
3. масштабируемость архитектуры для интеграции локальных моделей машинного обучения (семейства Gemma).

## 2.2 Модульная структура системы и технологический стек {#2.2-модульная-структура-системы-и-технологический-стек}

Архитектура платформы WISM (Web Intelligent Storyboard Maker) базируется на микросервисном подходе, обеспечивающем независимость функциональных блоков. Технологический стек выбран исходя из необходимости высокой скорости обработки данных и гибкости работы с ИИ-моделями:

1. Клиентский уровень (Frontend): разработан с использованием фреймворка Vue.js. Модуль отвечает за визуализацию иерархического древа истории и интерактивное взаимодействие пользователя с элементами генерации;  
2. Серверный уровень (Backend/Orchestrator): реализован на языке Python с применением фреймворка FastAPI. Данный модуль выполняет роль центрального оркестратора, координирующего потоки данных между пользователем, базами данных и генеративными моделями;  
3. Уровень асинхронных вычислений: для обработки длительных запросов к LLM и генерации контента интегрирован брокер задач Celery в связке с Redis. Это позволяет избежать блокировки основного потока приложения.

## 2.3 Организация гибридной системы хранения данных {#2.3-организация-гибридной-системы-хранения-данных}

Одной из центральных задач проектирования стала реализация системы хранения, способной эффективно обрабатывать нелинейные структуры. Для этого была спроектирована гибридная модель БД:

1. Реляционная БД (PostgreSQL): используется для хранения структурированных данных пользователей, профилей, прав доступа и базовых метаданных проектов. — Графовая БД (Neo4j): является основой для реализации нелинейного повествования. Каждый элемент истории (от Арки до Кадра) представляет собой узел в графе, а связи между ними определяют логику переходов и альтернативные ветки сюжета. Использование языка запросов Cypher позволяет оперативно извлекать цепочки событий любой сложности;  
2. Векторная БД (ChromaDB): применяется для реализации «нарративной памяти». В ней хранятся эмбеддинги текстовых описаний сцен и персонажей, что позволяет оркестратору осуществлять семантический поиск по контексту истории для передачи релевантных данных в LLM при генерации новых фрагментов.

## 2.4 Алгоритмы оркестрации и интеллектуального достраивания {#2.4-алгоритмы-оркестрации-и-интеллектуального-достраивания}

Логика взаимодействия компонентов при генерации контента управляется центральным оркестратором. Процесс «интеллектуального достраивания» (On-demand completion) реализуется по следующему алгоритму:

1. Инициация: пользователь отправляет запрос на заполнение пустой ветки или создание продолжения;  
2. Сбор контекста: оркестратор обращается к Neo4j для определения положения узла в графе и к ChromaDB для поиска семантически похожих фрагментов в рамках текущей ветки;  
3. Формирование промпта: полученный контекст объединяется с системными инструкциями и отправляется в модуль генерации (на текущем этапе — Google AI API, с последующим переходом на локальную модель Gemma-7b);  
4. Валидация и сохранение: полученный результат парсится в структурированный формат и записывается в соответствующие узлы графа Neo4j.

## 2.5 Проектирование 4-уровневой иерархии повествования {#2.5-проектирование-4-уровневой-иерархии-повествования}

Для обеспечения удобства навигации и логики работы ИИ-моделей в системе закреплена жесткая иерархия объектов: 

1. Story: корневой элемент проекта;  
2.  Arc: объединяет главы по крупным сюжетным целям;  
3. Chapter: функциональный блок, содержащий набор сцен;  
4. Scene: описывает конкретное местоположение и время (ключевой узел для векторного поиска);  
5. Frame: конечная единица визуализации, содержащая описание действия, диалог и визуальный промпт.

Спроектированная архитектура позволяет достичь высокого уровня автоматизации при сохранении возможности ручного редактирования каждого элемента, что отвечает целям разработки интеллектуального ассистента для создателей контента.

# 3 ПРОГРАММНАЯ РЕАЛИЗАЦИЯ СИСТЕМЫ {#3-программная-реализация-системы}

Программная реализация проекта представляет собой многокомпонентную систему, архитектура которой прошла значительную эволюцию в ходе разработки — от простого монолитного приложения до распределенной, асинхронной платформы. Этот путь был продиктован стремлением решить фундаментальные проблемы, связанные с производительностью, масштабируемостью и, что самое главное, с самой природой творческого процесса написания историй.

## 3.1 Эволюция архитектуры {#3.1-эволюция-архитектуры}

На начальном этапе проект был реализован в виде классического монолитного веб\-приложения. Единый сервис, построенный на фреймворке FastAPI, напрямую взаимодействовал с реляционной базой данных PostgreSQL и синхронно обрабатывал все запросы от клиентской части.

Такая архитектура, хотя и была проста в первоначальной реализации, быстро выявила свои критические недостатки в контексте поставленной задачи:

1. Блокировка пользовательского интерфейса: Наиболее ресурсоемкие операции, такие как генерация текста или анализ сюжета с помощью больших языковых моделей (LLM), занимали от нескольких секунд до десятков секунд. В синхронной модели это приводило к полной блокировке интерфейса на время выполнения запроса, что создавало крайне негативный пользовательский опыт (UX) и делало приложение практически неработоспособным.  
2. Несоответствие реляционной модели предметной области: Главная задача платформы — работа со сложными, многомерными связями между элементами повествования (персонажами, локациями, событиями, сюжетными арками). Попытки смоделировать эти отношения в реляционной базе данных PostgreSQL приводили к созданию громоздких связующих таблиц, усложнению запросов (множественные JOIN) и не позволяли эффективно выполнять запросы, естественные для анализа сюжета (например, "найти всех персонажей, не связанных ни с одним ключевым событием"). Фактически, реляционная модель заставляла "мыслить таблицами", в то время как предметная область требовала "мыслить связями".  
3. Проблемы с производительностью и масштабируемостью: По мере усложнения сюжета и роста количества сущностей, сложные запросы к PostgreSQL становились все более медленными. Масштабирование такой архитектуры представляло собой значительную трудность.

Осознание этих проблем привело к принятию двух фундаментальных, стратегических решений, которые полностью изменили архитектуру системы:

1. Переход к асинхронной, распределенной архитектуре: Было решено разделить систему на несколько взаимодействующих компонентов. Легковесный Orchestrator (FastAPI) остался в роли "диспетчера" HTTP-запросов, а все "тяжелые" вычисления были вынесены в асинхронные фоновые задачи, выполняемые сервисом Worker (Celery). Это позволило мгновенно возвращать ответ пользователю, не дожидаясь завершения долгих операций.  
2. Миграция на графовую модель данных: Для решения проблемы моделирования сложных связей был совершен полный отказ от реляционной базы данных в пользу графовой СУБД Neo4j. Этот выбор позволил естественным образом представлять структуру повествования в виде графа, где персонажи, главы и события являются узлами, а их взаимоотношения — ребрами. Это не только упростило хранение данных, но и открыло возможности для молниеносного выполнения сложных аналитических запросов по структуре сюжета.

Таким образом, финальная архитектура представляет собой современную, распределенную систему, в основе которой лежит графовая модель данных, что наиболее полно соответствует задачам создания и интеллектуального анализа сложных, нелинейных историй. Далее будут подробно рассмотрены ключевые компоненты этой системы.

## 3.2 Графовая модель данных как фундамент системы {#3.2-графовая-модель-данных-как-фундамент-системы}

Центральным элементом обновленной архитектуры является модель данных, реализованная на базе графовой СУБД Neo4j. Переход от реляционной к графовой парадигме стал ключевым решением, которое позволило преодолеть фундаментальные ограничения предыдущего подхода и создать по-настоящему гибкую и масштабируемую систему.

### 3.2.1 Обоснование выбора {#3.2.1-обоснование-выбора}

Реляционные базы данных, такие как PostgreSQL, оперируют сущностями, хранящимися в таблицах. Связи между ними являются вторичными и устанавливаются во время запроса с помощью операций JOIN. Для моделирования сложной, многоуровневой и нелинейной структуры повествования такой подход оказался контринтуитивным и неэффективным. Он требовал создания множества связующих таблиц, а запросы для навигации по сюжету (например, "найти все сцены в данной арке, в которых появляется этот персонаж, и которые предшествуют сцене кульминации") становились чрезвычайно громоздкими и медленными.

В отличие от этого, графовые базы данных ставят во главу угла именно отношения (связи) между данными. Данные хранятся в виде узлов, а связи между ними являются первоклассными элементами модели, что позволяет выполнять обход графа и сложные запросы на порядки быстрее. Этот подход позволил перейти от "мышления таблицами" к "мышлению связями", что идеально соответствует предметной области сторителлинга.

### 3.2.2 Проектирование “анатомии” повествования {#3.2.2-проектирование-“анатомии”-повествования}

В Neo4j вся структура истории представлена в виде единого графа, где каждый элемент повествования является узлом с определенными свойствами и метками, а его взаимодействие с другими элементами описывается направленными типизированными связями.

Были определены следующие типы узлов, формирующие иерархию повествования:

1. Story: Корневой узел, представляющий всю историю целиком.  
2. Arc: Крупный сюжетный блок, объединяющий несколько глав (например, "Завязка", "Противостояние", "Развязка").  
3. Chapter: Глава истории, содержащая набор сцен.  
4. Scene: Логически завершенный отрезок повествования, происходящий в одном месте и в одно время.  
5. Frame: Минимальная единица повествования, "кадр" истории, содержащий описание для последующей генерации изображения.  
6. Entity: Сущность мира истории (персонаж, локация, предмет), которая может быть связана с любым другим узлом.

Ключевой инновацией в спроектированной модели является введение специального мета-узла BranchSet. В отличие от других узлов, он не несет в себе контентной нагрузки (текста или описания). Его единственная задача — служить структурным контейнером для явного определения точек ветвления и слияния сюжета.

Например, если одна сцена может вести к двум разным исходам, она будет связана не напрямую с этими двумя сценами, а с узлом BranchSet, который, в свою очередь, будет содержать обе альтернативные сцены. Это решение позволило:

1. Сделать замысел автора явным: Структура данных теперь сама по себе говорит: "здесь находится точка выбора".  
2. Радикально упростить логику UI: Вместо того чтобы клиентскому приложению приходилось анализировать сложный клубок связей для "обнаружения" ветвления, ему достаточно увидеть узел BranchSet и применить соответствующую логику визуализации. Вся сложность инкапсулируется на уровне модели данных.

Взаимодействия между узлами описываются следующими типами связей:

1. :CONTAINS: Описывает вертикальную иерархию "родитель-ребенок". Например, (:Arc)-\[:CONTAINS\]-\>(:Chapter). Эта связь определяет принадлежность.  
2. :NEXT: Описывает горизонтальную последовательность на одном уровне иерархии. Именно этот тип связи формирует повествовательную цепочку и реализует ветвления. Наличие нескольких исходящих связей :NEXT от одного узла (или от узла BranchSet) естественным образом создает развилку сюжета.

Такая продуманная графовая модель стала прочным фундаментом, на котором была построена вся остальная логика приложения, от API на бэкенде до управления состоянием на фронтенде.

## 3.3 Архитектура Backend {#3.3-архитектура-backend}

На фундаменте графовой модели данных был возведен "мозг" системы — распределенная бэкенд-архитектура, спроектированная для решения двух ключевых задач: обеспечения отзывчивости интерфейса и эффективного выполнения ресурсоемких операций.

### 3.3.1 Разделение ответственности {#3.3.1-разделение-ответственности}

Для достижения максимальной производительности и масштабируемости была внедрена архитектура с разделением ответственности, состоящая из двух ключевых сервисов:

1. Orchestrator (FastAPI): Этот сервис представляет собой легковесный API-шлюз. Его основная задача — принимать HTTP-запросы от клиентского приложения, проводить их быструю валидацию и выступать в роли "диспетчера". Он не выполняет никаких долгих вычислений. Вместо этого, для ресурсоемких операций, он создает задачу и отправляет ее в очередь для Worker'а, немедленно возвращая клиенту ответ 202 Accepted. Это позволяет пользовательскому интерфейсу оставаться полностью интерактивным.  
2. Worker (Celery): Это асинхронный сервис, который постоянно слушает очередь задач. Он выполняет все "тяжелые" операции:  
   1. Обращения к API больших языковых моделей (LLM) для генерации текста.  
   2. Анализ сюжета и извлечение сущностей.  
   3. Сложные транзакции в базе данных.

Такое разделение гарантирует, что долгие процессы не блокируют основной поток приложения и могут быть легко масштабированы горизонтально путем запуска дополнительных экземпляров Worker'ов.

### 3.3.2 Коммуникация и уведомления {#3.3.2-коммуникация-и-уведомления}

Ключевой сложностью в асинхронной архитектуре является информирование клиента о статусе выполнения фоновой задачи. Эта проблема была решена с помощью элегантного паттерна "Издатель-подписчик" (Pub/Sub), реализованного на базе Redis.

1. Redis используется не только как брокер сообщений для Celery, но и как высокопроизводительная шина для обмена сообщениями в реальном времени.  
2. После завершения задачи (успешно или с ошибкой) Worker публикует (publishes) сообщение с результатом в специальный канал в Redis.  
3. Сервис Orchestrator постоянно подписан (subscribes) на этот канал. Получив сообщение, он немедленно транслирует его нужному клиенту через постоянное WebSocket-соединение.

Эта схема позволяет надежно и с минимальной задержкой доставлять уведомления на фронтенд, информируя пользователя о завершении генерации, появлении новых элементов или возникновении ошибок.

### 3.3.3 API для работы с графом {#3.3.3-api-для-работы-с-графом}

Для эффективного взаимодействия с графовой моделью и минимизации логики на стороне клиента был спроектирован специальный API. Вместо того чтобы заставлять фронтенд делать множество запросов и самостоятельно собирать "сцену", был создан ключевой эндпоинт: “GET /api/context/{nodeId}”.

Этот API-вызов является краеугольным камнем взаимодействия фронтенда и бэкенда. Он возвращает не просто прямых потомков запрошенного узла, а так называемый "обогащенный контекст" — один плоский, заранее упорядоченный массив узлов, представляющий собой "окно" повествования вокруг центрального элемента.

Каждый узел в этом массиве "обогащен" дополнительной информацией, необходимой для рендеринга:

1. Информация о родителе (parent): ID, тип и заголовок родительского узла, что необходимо для построения навигационных "хлебных крошек".  
2. Информация о ветвлении (branch\_info): Специальный флаг is\_branch\_point и список доступных веток, если данный узел является точкой сюжетного выбора (ссылается на BranchSet).

Такой подход инкапсулирует всю сложность обхода графа на бэкенде. Фронтенд получает готовые к отображению, простые для итерации данные, что делает его код значительно чище, а производительность — выше. Это классический пример правильного распределения ответственности, где "умный" бэкенд обслуживает "глупый", но быстрый фронтенд.

## 3.4 Архитектура Frontend {#3.4-архитектура-frontend}

Клиентская часть приложения, разработанная на фреймворке Vue.js, является не просто системой для отображения данных, а сложным инструментом для взаимодействия с нелинейной структурой повествования. Ее архитектура была спроектирована с целью обеспечить максимальную производительность, предсказуемость и надежность, даже при работе с очень сложными графами сюжета.

### 3.4.1 Управление состоянием Pinia {#3.4.1-управление-состоянием-pinia}

В основе архитектуры фронтенда лежит централизованное управление состоянием с помощью библиотеки Pinia. Логика разделена на два ключевых хранилища (stores), каждое из которых решает свою, строго определенную задачу:

1. orchestrationStore и "Очередь Действий" (Action Queue): Это хранилище реализует стратегически важное решение для обеспечения целостности данных. Вместо немедленной отправки каждого изменения на сервер, что в асинхронной среде чревато состоянием гонки и рассинхронизацией, был внедрен паттерн "Очередь Действий".  
   1. Принцип работы: Любое действие пользователя, изменяющее структуру или содержание (создание, удаление, обновление, запуск генерации), не отправляется на сервер немедленно. Вместо этого, оно добавляется в виде объекта-команды в очередь в orchestrationStore.  
   2. Предпросмотр: Пользовательский интерфейс реактивно "читает" эту очередь и отображает "предпросмотр" будущих изменений. Например, элемент, помеченный на удаление, может стать полупрозрачным, а новый, генерируемый элемент, будет показан как плейсхолдер.  
   3. Атомарное применение: Только после того, как пользователь нажимает кнопку "Применить", вся очередь действий отправляется на бэкенд одним-единственным атомарным запросом. Бэкенд получает полный "план" изменений и выполняет их в рамках одной транзакции. Этот подход гарантирует, что зависимые операции (например, генерация, которая должна выполняться на очищенных данных) всегда работают с актуальным и целостным состоянием.  
2. contentStore и "Нормализованный кэш": Это хранилище отвечает за эффективное получение, кэширование и предоставление данных для отображения. Для решения проблем с дублированием и рассинхронизацией данных, которые неизбежно возникают при работе со сложными графами, был реализован паттерн "Нормализованный кэш".  
   1. Структура: Кэш состоит из двух Map-объектов:  
      1. nodes: Map\<string, StoryNode\>: Единый источник правды. Это плоская таблица, где каждый узел (сцена, глава, арка) хранится только один раз по своему уникальному id.  
      2. contexts: Map\<string, string\[\]\>: Хранилище, которое для каждого загруженного "окна" (context) содержит только упорядоченный массив ID узлов.  
   2. Принцип работы: Когда с бэкенда приходит массив "обогащенных" узлов, contentStore разбирает его: каждый узел помещается/обновляется в nodes, а массив их ID сохраняется в contexts. Компоненты для отображения запрашивают у getter-а нужный контекст, который "на лету" собирается из contexts и nodes.  
   3. Преимущества: Такой подход гарантирует отсутствие дублирования данных, консистентность (обновление узла в nodes автоматически отражается во всех частях интерфейса) и обеспечивает мгновенную навигацию по уже посещенным разделам, так как данные берутся напрямую из кэша без сетевых запросов.

   ### 3.4.2 Визуализация нелинейности {#3.4.2-визуализация-нелинейности}

На базе этих хранилищ была построена система визуализации:

1. TimelineView — "Ленивый" компонент: Благодаря тому, что бэкенд и contentStore берут на себя всю сложную работу по подготовке и упорядочиванию данных, основной компонент для отображения таймлайна (TimelineView) остается архитектурно простым. Его задача сводится к итерации по готовому, упорядоченному списку узлов и их отображению.  
2. "Магистральный сюжет" и "Ленивая загрузка": Для обеспечения высокой производительности на уровнях с сотнями и тысячами узлов, система не пытается загрузить их все сразу. API возвращает только "магистральную" сюжетную линию, а наличие побочных веток помечается специальной иконкой. Пользователь может "лениво" подгрузить интересующую его ветку, кликнув на эту иконку, что инициирует новый, целевой запрос к API.

   ### 3.4.3 Визуальный конструктор структуры {#3.4.3-визуальный-конструктор-структуры}

Финальным штрихом архитектуры фронтенда является реализация уникального пользовательского опыта в виде "недеструктивного монтажного стола". Этот интерфейс позволяет пользователю импортировать большой, неструктурированный текст и визуально "нарезать" его на структурные блоки (Арки, Главы, Сцены), которые затем выстраиваются в иерархическую и временную линию повествования, полностью используя описанные выше механизмы работы с данными.

4 ОБОСНОВАНИЕ КЛЮЧЕВЫХ АРХИТЕКТУРНЫХ РЕШЕНИЙ

В процессе разработки платформы были приняты несколько стратегических архитектурных решений, которые фундаментально определили ее итоговый облик, производительность и надежность. Данный раздел посвящен обоснованию этих решений путем анализа рассмотренных альтернатив и причин, по которым был сделан окончательный выбор.

## 4.1 Выбор модели данных. Реляционный подход против графового {#4.1-выбор-модели-данных.-реляционный-подход-против-графового}

Проблема: На начальном этапе разработки была предпринята попытка смоделировать структуру повествования с помощью реляционной СУБД PostgreSQL. Вскоре стало очевидно, что этот подход неэффективен и контринтуитивен. Моделирование нелинейных и многомерных сюжетных связей (ветвления, слияния, отношения персонажей) требовало создания громоздких связующих таблиц, а навигационные запросы (например, "получить все сцены, следующие за данной, по всем веткам") выливались в сложные и медленные JOIN-операции, что становилось "узким местом" всей системы.

Рассмотренные альтернативы:

1. Реляционная модель (PostgreSQL): Продолжать использование PostgreSQL, оптимизируя запросы с помощью рекурсивных CTE (Common Table Expressions) и сложных хранимых процедур.  
2. Графовая модель (Neo4j): Перейти на нативную графовую СУБД, где узлы и связи являются первоклассными элементами модели.

Принятое решение: Была совершена полная миграция с PostgreSQL на графовую СУБД Neo4j.

Обоснование: Данное решение было продиктовано следующими причинами:

1. Прямое соответствие предметной области: Графовая парадигма позволяет "мыслить связями", что идеально соответствует природе повествования. Структура сюжета естественным образом представляется в виде графа узлов и ребер.  
2. Производительность: Графовые СУБД оптимизированы для быстрых навигационных запросов (обхода графа). Это позволило кардинально, на порядок, ускорить получение контекста для любого узла истории.  
3. Гибкость и упрощение разработки: Добавление новых типов связей или узлов в графовую модель происходит значительно проще, чем изменение сложной схемы реляционной базы данных. Это удешевило и ускорило разработку сложной бизнес-логики.

## 4.2 Управление изменениями. Чистый UNDO\\REDO против очереди действий {#4.2-управление-изменениями.-чистый-undo\redo-против-очереди-действий}

Проблема: В системе, где выполняются долгие асинхронные операции (генерация текста), возникает критический риск состояния гонки (race condition). Если пользователь инициирует несколько зависимых друг от друга действий подряд (например, "удалить сцену", а затем "сгенерировать главу", которая зависит от отсутствия этой сцены), нет никакой гарантии правильного порядка их выполнения на сервере, что может привести к нарушению целостности данных.

Рассмотренные альтернативы:

1. Классический паттерн "Команда" (Undo/Redo): Немедленно выполнять каждое действие и реализовывать для него обратную операцию undo(). Этот подход интуитивен для пользователя, но сложен в реализации для асинхронных, транзакционных систем.  
2. Паттерн "Очередь Действий" (Action Queue): Накапливать все изменения на стороне клиента в виде очереди ("пачки") и отправлять их на сервер для выполнения единой атомарной транзакцией.

Принятое решение: Была реализована архитектура "Очереди действий" в хранилище orchestrationStore.

Обоснование: Данный подход был выбран как объективно более надежный для этого класса систем. Он гарантирует транзакционную целостность пользовательской сессии: вся "пачка" изменений либо применяется успешно целиком, либо не применяется вовсе. Это полностью устраняет класс ошибок, связанных с нарушением порядка асинхронных операций, и обеспечивает предсказуемое, консистентное состояние системы. При этом данный подход служит идеальным фундаментом для будущей реализации Undo/Redo на более высоком уровне — на уровне отмены целых "пачек" изменений.

## 4.3 Проектирование API. Болтливый API против обогащенный контекст {#4.3-проектирование-api.-болтливый-api-против-обогащенный-контекст}

Проблема: При использовании классического RESTful-подхода для сборки одного экрана (например, таймлайна) клиенту пришлось бы выполнять множество последовательных запросов: сначала получить арку, затем ее главы, затем сцены для каждой главы и т.д. Этот паттерн, известный как "Chatty I/O" ("болтливый" ввод-вывод), усложняет логику фронтенда, увеличивает общее время загрузки и нагрузку на сеть.

Рассмотренные альтернативы:

1. Классический RESTful API: Реализовать отдельные эндпоинты для каждого типа ресурсов (/api/arcs/{id}, /api/chapters/{id} и т.д.).  
2. API с "Обогащенным контекстом": Создать единый эндпоинт, который инкапсулирует всю сложность обхода графа на сервере и возвращает клиенту готовый к отображению, плоский и упорядоченный набор данных.

Принятое решение: Был спроектирован и реализован ключевой эндпоинт GET /api/context/{id}.

Обоснование: Это решение основано на принципе "умный бэкенд, глупый фронтенд". Вся сложность по навигации в графе, определению веток и подготовке данных к визуализации перенесена на сервер. Клиентское приложение получает простые, готовые к использованию данные, что позволило:

1. Радикально упростить код на фронтенде.  
2. Значительно повысить производительность UI за счет сокращения количества HTTP-запросов.  
3. Сделать всю систему более гибкой и поддерживаемой, так как изменение логики обхода графа требует модификации только в одном месте на бэкенде.

## 4.4 Вывод по главе {#4.4-вывод-по-главе}

Принятые архитектурные решения — переход на графовую модель данных, внедрение "очереди действий" для управления изменениями и проектирование "обогащенного" API — не являются изолированными улучшениями. Они представляют собой взаимосвязанный комплекс мер, который позволил решить фундаментальные проблемы, присущие данному классу систем: производительность при работе со сложными связями, целостность данных в асинхронной среде и сложность клиентской логики.

Каждый из этих осознанных выборов демонстрирует приверженность принципам построения надежных и масштабируемых систем. В совокупности они обеспечили синергетический эффект, превратив первоначальную концепцию в архитектурно зрелую и высокопроизводительную платформу. Именно этот продуманный инженерный подход является залогом успешной реализации проекта и прочным фундаментом для его дальнейшего развития.

# 5 ТЕСТИРОВАНИЕ И ОЦЕНКА РЕЗУЛЬТАТОВ {#5-тестирование-и-оценка-результатов}

Процесс тестирования и оценки системы был неотъемлемой частью разработки и выходил далеко за рамки простого поиска функциональных ошибок. Он служил инструментом для валидации архитектурных гипотез и стал катализатором для ключевых инженерных решений, которые кардинально улучшили производительность и надежность платформы. Оценка проводилась на двух взаимосвязанных уровнях:

1. Технический уровень: Оценка производительности серверной части, масштабируемости архитектуры и надежности механизмов обработки данных.  
2. Пользовательский уровень: Оценка отзывчивости интерфейса, предсказуемости его поведения и общего качества пользовательского опыта (UX) при взаимодействии со сложными структурами данных.

Далее представлены три ключевых кейса, демонстрирующих, как итеративный подход к тестированию привел к созданию отказоустойчивой и высокопроизводительной системы.

## 5.1 Кейс №1: решение производительности бэкенда {#5.1-кейс-№1:-решение-производительности-бэкенда}

Проблема заключалась в том, что на этапе нагрузочного тестирования первоначальной архитектуры, основанной на PostgreSQL, было выявлено критическое "узкое место". Запросы, требующие сбора контекста для определенного узла повествования (например, всех сцен в главе вместе с их персонажами и локациями), требовали выполнения множества JOIN-операций. По мере роста сложности сюжета время ответа сервера на такие запросы экспоненциально росло, что приводило к длительным задержкам в UI и, в конечном итоге, к ошибкам ResponseValidationError из\-за превышения таймаутов.

Была выдвинута гипотеза, что миграция на графовую СУБД кардинально ускорит подобные запросы за счет нативной поддержки связей. Для проверки этой гипотезы была создана тестовая среда с идентичным набором данных в Neo4j и реализован ключевой эндпоинт GET /api/context/{id}, логика которого была основана на обходе графа.

Оценка результатов. Результаты тестирования подтвердили гипотезу со значительным превосходством:

Качественное улучшение производительности: Время выполнения запросов на получение контекста сократилось на порядок. Операции, которые в PostgreSQL занимали несколько секунд, в Neo4j выполнялись за десятки миллисекунд.

Новые функциональные возможности: Графовая модель позволила реализовать сложные аналитические запросы, которые в реляционной модели были бы крайне непрактичными. Например, стало возможным мгновенно находить "изолированные" ветки сюжета (узлы, не имеющие входящих :NEXT связей) или отслеживать пути персонажей через все повествование.

## 5.2 Кейс №2: устранение задержек и рассинхронизации в UI {#5.2-кейс-№2:-устранение-задержек-и-рассинхронизации-в-ui}

Проблема: При тестировании пользовательского интерфейса были выявлены две взаимосвязанные проблемы, серьезно ухудшающие UX. Во-первых, наблюдались заметные задержки и "мерцание" данных при переключении между экранами, так как данные каждый раз запрашивались с сервера заново. Во-вторых, был обнаружен критический баг: обновление данных в одном компоненте (например, изменение заголовка сцены в боковой панели) не всегда отражалось в другом компоненте (например, на таймлайне), где использовался тот же узел. Это приводило к рассинхронизации состояния и потере доверия пользователя к интерфейсу.

Тестирование гипотезы: Для решения этой проблемы была предложена реализация "нормализованного кэша" в contentStore (Pinia). Гипотеза заключалась в том, что единый источник правды для всех данных (nodes Map) и кэширование загруженных контекстов (contexts Map) решат обе проблемы одновременно.

Оценка результатов: Внедрение нормализованного кэша привело к следующим измеримым улучшениям:

Производительность интерфейса: Навигация "вверх" по иерархии и возврат к уже посещенным разделам стали мгновенными. Данные извлекались напрямую из кэша, что полностью исключало сетевые задержки.

Надежность и консистентность: Проблема рассинхронизации состояния была полностью устранена. Благодаря единому источнику правды, любое изменение узла, зафиксированное в nodes Map, реактивно и гарантированно распространялось по всем компонентам приложения, использующим этот узел.

## 5.3 Кейс №3: Обеспечение целостности данных при асинхронных операциях {#5.3-кейс-№3:-обеспечение-целостности-данных-при-асинхронных-операциях}

Проблема: Наиболее опасный класс ошибок был выявлен не при тестировании, а на этапе архитектурного проектирования асинхронного взаимодействия. Это проблема состояния гонки (race condition). Пример: пользователь инициирует два действия подряд — 1\) удалить сцену, 2\) сгенерировать новую главу, логика которой зависит от отсутствия удаленной сцены. При отправке двух отдельных асинхронных запросов не было никакой гарантии, что операция удаления завершится до начала операции генерации. Это могло привести к генерации на неактуальных данных или к непредвиденным ошибкам.

Тестирование гипотезы: Была спроектирована и реализована архитектура orchestrationStore с "очередью действий". Гипотеза состояла в том, что группировка всех пользовательских изменений в "пачку" и их отправка единой транзакцией обеспечит атомарность и правильный порядок выполнения.

Оценка результатов: Тестирование подтвердило, что данный подход полностью решает поставленную проблему:

Надежность системы: Система стала транзакционно-устойчивой на уровне пользовательских сессий. Вся пачка изменений либо успешно применяется на бэкенде целиком, либо не применяется вовсе. Это полностью исключает весь класс ошибок, связанных с нарушением порядка асинхронных операций, состоянием гонки и частичным применением изменений. Пользователь может быть уверен, что состояние системы всегда остается целостным.

## 5.4 Итоговая оценка {#5.4-итоговая-оценка}

Итеративный подход к тестированию, при котором оценка результатов служила основанием для принятия смелых архитектурных решений, позволил последовательно устранить фундаментальные недостатки первоначальной реализации. Внедрение графовой базы данных, нормализованного кэша на клиенте и транзакционной "очереди действий" превратило прототип в высокопроизводительную, надежную и масштабируемую платформу, способную эффективно работать со сложными нелинейными структурами данных, что полностью соответствует поставленным целям проекта.

В процессе исследования и разработки были достигнуты следующие ключевые результаты:

1. Разработана и внедрена эффективная графовая модель данных на базе Neo4j. Был совершен осознанный отказ от реляционной модели, ограничения которой не позволяли эффективно работать со сложными сюжетными связями. Новая модель, основанная на узлах (Node) и связях (Relationship), позволила естественным образом представить иерархию и нелинейную последовательность повествования. Ключевой инновацией стало введение структурного мета-узла BranchSet, который позволил явно моделировать точки ветвления и слияния сюжета, радикально упростив логику навигации и визуализации на стороне клиента.  
2. Построена отказоустойчивая, асинхронная бэкенд-архитектура. Для решения проблемы блокировки интерфейса при выполнении ресурсоемких операций была внедрена распределенная архитектура. Она включает в себя легковесный API-шлюз Orchestrator (FastAPI) и масштабируемый сервис для фоновых вычислений Worker (Celery). Взаимодействие между ними и информирование клиента о статусе задач реализовано через надежный паттерн "Издатель-подписчик" (Pub/Sub) на базе Redis, что обеспечивает высокую отзывчивость системы.  
3. Создан продвинутый и производительный пользовательский интерфейс. Архитектура фронтенда основана на двух мощных паттернах управления состоянием, которые обеспечивают его надежность и скорость:  
   1. "Нормализованный кэш" в contentStore решил проблему рассинхронизации и дублирования данных, создав единый источник правды для всех сущностей и обеспечив мгновенную навигацию по ранее загруженным разделам.  
   2. "Очередь действий" (Action Queue) в orchestrationStore стала ключевым решением для обеспечения целостности данных. Этот механизм группирует все пользовательские изменения и отправляет их на сервер единой атомарной транзакцией, что полностью исключает класс ошибок, связанных с состоянием гонки в асинхронной среде.  
4. Спроектирован уникальный пользовательский опыт (UX) в виде "недеструктивного монтажного стола". Этот интерфейс, ставший возможным благодаря описанной выше архитектуре, позволяет автору визуально конструировать структуру повествования из сырого текста, что является значительным шагом вперед по сравнению с традиционными линейными редакторами.

Практическая значимость работы подтверждается разработанным прототипом платформы WISM, который демонстрирует возможность значительного снижения порога вхождения в сферу создания визуального контента. Платформа позволяет сократить время на превизуализацию и прототипирование комиксов и сторибордов в несколько раз по сравнению с традиционными методами.

Перспективы дальнейшего развития проекта включают в себя:

1. Полный переход на локальные модели (Gemma-7b) для обеспечения автономности системы.  
2. Интеграцию модулей генерации изображений (Stable Diffusion) с использованием технологий ControlNet для обеспечения персонажной консистентности.  
3. Добавление инструментов для экспорта готового контента в различных медиа-форматах.

Таким образом, поставленная в начале работы цель — разработка прототипа интеллектуальной платформы для сквозной генерации контента — была полностью достигнута. В результате проделанной работы была создана не просто рабочая программа, а архитектурно зрелый фундамент для дальнейшего развития платформы. Итеративный подход к проектированию и тестированию, готовность к кардинальному пересмотру первоначальных решений и применение современных инженерных практик позволили успешно достичь и даже превзойти изначально поставленные цели.
