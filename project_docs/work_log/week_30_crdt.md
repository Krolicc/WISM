Чтобы избежать лишней работы и не писать код «в стол», мы пойдем по пути наслоения: каждый следующий этап будет не переписывать предыдущий, а расширять его функции.

Вот роудмап эволюции от простого общего стейта до твоей системы с черновиками и корзиной.

Этап 1: "Single Source of Truth" (Чистый CRDT)
Цель: Запустить общую синхронизацию без бизнес-логики.

Что делаем: Подключаем библиотеку (например, Yjs) и IndexedDB для офлайна. Создаем одну общую Y.Map или Y.Array для узлов графа.

Логика: Клиент меняет данные напрямую -> все видят результат.

Почему это не лишний код: Это фундамент. Даже в финальной версии тебе нужно будет синхронизировать простые поля (координаты, цвета).

Результат: У тебя есть база, которая работает в офлайне и решает конфликты на уровне типов данных.

Этап 2: "Status Overlay" (Подготовка к валидации)
Цель: Научить UI понимать, что данные могут быть в разных состояниях, не меняя структуру.

Что делаем: В модель данных узла добавляем поле syncStatus (по умолчанию 'ok').

Логика: В коде фронтенда прописываем условие: если status === 'pending', рисуй узел полупрозрачным.

Почему это не лишний код: Твой UI в любом случае должен уметь отображать разные состояния. Мы просто вводим это правило заранее.

Результат: Ты визуально видишь разницу между тем, что ты «нажал», и тем, что «сохранилось», хотя сервера еще может не быть.

Этап 3: "Server as a Peer" (Внедрение бизнес-логики)
Цель: Подключить сервер к WebSocket-каналу как полноценного участника (Headless Client).

Что делаем: Сервер подписывается на изменения CRDT-документа. Как только прилетает новый узел с syncStatus: 'pending':

Сервер проверяет его (Neo4j транзакция).

Если ок: сервер сам меняет в CRDT syncStatus на 'ok'.

Если ошибка: сервер меняет на 'rejected' и пишет errorMessage.

Почему это не лишний код: Это и есть твоя будущая бизнес-логика. Мы просто перенесли её выполнение с прямого HTTP-запроса на наблюдение за стейтом.

Результат: Появилась "высшая сила" (сервер), которая одобряет или отклоняет правки.

Этап 4: "The Staging Area" (Черновики и Корзина)
Цель: Финализация архитектуры: отделение мусора от чистовика.

Что делаем: Вместо одной общей папки в CRDT создаем две: doc.getMap('main') и doc.getMap('staging').

Логика:

Новые узлы всегда создаются в staging.

Сервер при успехе переносит (копирует в main и удаляет из staging) узел.

При ошибке — оставляет в staging с пометкой rejected.

Почему это не лишний код: На этом этапе ты просто меняешь "адрес" записи данных. Весь код UI из Этапа 2 и логика сервера из Этапа 3 остаются прежними, меняются только пути в объекте.

Результат: Чистая база Neo4j и CRDT-документ, где черновики не мешают основной работе.

Этап 5: "Garbage Collection" (Авто-очистка)
Цель: Гигиена данных.

Что делаем: Пишем один небольшой скрипт на сервере (Cron-задача), который раз в сутки проходит по doc.getMap('staging') и удаляет всё, что старше 7 дней или имеет статус rejected дольше суток.

Результат: Твой IndexedDB у пользователей не раздувается до бесконечности.

Итоговая схема потока данных:
Резюме по коду (как не писать лишнего):
UI: Сразу пиши компоненты так, чтобы они принимали объект и визуально зависели от его внутреннего поля status.

ID: С самого первого этапа используй только клиентские UUID.

Транспорт: Сразу делай WebSocket-обертку, которая может переваривать и бинарные данные CRDT, и твои JSON-команды (если решишь их оставить).

Архитектура синхронизации субдокументов (pycrdt + Yjs)

1. Структура данных

Root Doc (Главный): Содержит Y.Map (назовем её shelves_registry).

Ключ: shelf_id (string).

Значение: Y.Doc (инстанс субдокумента).

Sub Doc (Полочка): Содержит тяжелые данные (тексты, массивы, другие карты).

2. Фронтенд (Vue 3 + Yjs)

А. Регистрация субдокумента

При инициализации приложения или получении списка полочек, вы только создаете "пустышки" в реестре:

// В главном документе
const subdoc = new Y.Doc({ guid: shelfId, shouldLoad: false });
shelvesRegistry.set(shelfId, subdoc);


Б. Жизненный цикл компонента "Полочка"

Внутри Vue-компонента полочки:

onMounted:

Вызываем subdoc.load(). Это переводит subdoc.shouldLoad в true и вызывает событие subdocs у корневого документа.

Подписываемся на изменения внутри subdoc для обновления UI.

onUnmounted:

Вызываем subdoc.destroy(). Это освобождает память и сигнализирует провайдеру о прекращении подписки.

В. Мультиплексированный провайдер (Custom Provider)

Вместо стандартного провайдера используем логику, которая слушает события корневого документа:

rootDoc.on('subdocs', ({ loaded, added, removed }) => {
    loaded.forEach(subdoc => {
        // Отправляем на бэкенд запрос: "Я хочу получать данные для subdoc.guid"
        sendWsMessage({ type: 'subscribe', docId: subdoc.guid });
        
        // При получении данных от WS:
        // Y.applyUpdate(subdoc, updateFromBackend);
    });
});


3. Протокол обмена (WebSocket JSON + Binary)

Чтобы передавать бинарные данные CRDT внутри одного сокета, используйте обертку:

Запрос подписки: {"action": "sub", "id": "shelf_1"}

Передача апдейта: {"action": "update", "id": "shelf_1", "data": "<base64_or_binary>"}

4. Бэкенд (Python + pycrdt)

А. Менеджер документов

Создайте класс DocManager, который хранит словарь активных документов:
self.active_docs = { "doc_id": {"doc": pycrdt.Doc, "users": set(user_ids)} }

Б. Обработка входящих сообщений

Action: "sub"

Проверка прав: Проверить через БД, может ли user_id смотреть shelf_id.

Загрузка: Если документа нет в active_docs, загрузить bytes из БД и создать pycrdt.Doc.

Синхронизация: Отправить пользователю текущий стейт документа: get_update(doc).

Action: "update"

Применить апдейт к документу: doc.apply_update(data).

Разослать этот апдейт всем остальным участникам, подписанным на этот id.

В. Persistence (Сохранение в БД)

Используйте механизм Debounce для каждой полочки:

При каждом update обновляем last_modified в словаре.

Раз в 5-10 секунд фоновая задача (через asyncio) проверяет документы и, если были изменения, сохраняет get_update(doc) в БД (поле типа BYTEA/BLOB).

5. Очистка (Lifecycle Management)

На бэкенде:

Когда пользователь закрывает сокет или присылает "unsub":

Удаляем user_id из списка слушателей конкретного doc_id.

Важно: Если список слушателей пуст:

Делаем финальное сохранение в БД.

Удаляем документ из self.active_docs, чтобы не забивать RAM.

На фронтенде:

subdoc.destroy() автоматически уберет его из списка загруженных.

Не забывайте очищать кэш в браузере, если используете IndexedDB.

6. Мельчайшие нюансы (Edge Cases)

Конфликт создания: Если два пользователя одновременно создали субдокумент с одним ID, Yjs выберет один на основе clientId. Бэкенд должен просто игнорировать повторное создание и отдавать существующий.

Размер сообщения: Если полочка очень тяжелая, при первом sub апдейт может быть большим. Убедитесь, что ваш WS-сервер поддерживает большие фреймы.

Версионность: Храните в БД не только бинарный апдейт, но и версию схемы, если планируете менять структуру данных в будущем.
