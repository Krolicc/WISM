# Неделя 17: Proof of Concept — Интеллектуальный анализ сюжета

На этой неделе мы начинаем работу над революционной функцией, которая выведет платформу на новый уровень: переход от простого создания контента к его интеллектуальному анализу и реструктуризации. Это позволит пользователям загружать существующие сюжеты и тексты для их глубокой проработки.

### Глобальная цель: 
Разработать функционал для анализа и структурирования пользовательских текстов, используя Графы Знаний (Knowledge Graphs) и LLM.

### Задачи-кандидаты:
1.  **Анализ сюжета:** Загрузка синопсиса, построение графа связей (персонажи, локации, события), автоматический поиск сюжетных дыр (например, "висячие" персонажи, неиспользуемые предметы, логические разрывы).
2.  **Декомпозиция текста:** Загрузка готового художественного текста и его автоматическое разложение на иерархическую структуру: История -> Главы -> Сцены -> Кадры.

### Цель на неделю: Proof of Concept (PoC) для Задачи №1

**Задача:** Создать изолированный прототип, доказывающий жизнеспособность идеи. Он должен принять на вход короткий сюжет, построить по нему граф знаний и найти хотя бы один тип сюжетной несостыковки.

### Детальный план работы:

1.  **Проектирование и Промпт-Инжиниринг (1-2 дня):**
    *   **Задача:** Сформулировать и отточить основной промпт для LLM.
    *   **Критерий успеха:** Промпт должен стабильно извлекать из текста сюжета ключевые сущности (персонажи, предметы, локации, события) и отношения между ними в строго определенном JSON-формате.

2.  **Разработка "Парсера" и "Строителя графа" (1-2 дня):**
    *   **Задача:** Написать Python-скрипт, который будет принимать текст, вызывать LLM с разработанным промптом, парсить полученный JSON и строить из него граф в памяти.
    *   **Инструменты:** `requests` (или `httpx`) для API-вызовов, `networkx` для создания и управления графом.

3.  **Разработка "Анализатора графа" (1 день):**
    *   **Задача:** Реализовать в скрипте 1-2 базовые функции для анализа построенного графа.
    *   **Примеры проверок:**
        *   Поиск "изолированных узлов": персонажей, у которых менее 2 связей с другими сущностями.
        *   Поиск "неиспользуемых ружей Чехова": важных предметов, которые не участвуют ни в одном событии.

4.  **Создание минималистичного UI для демонстрации (1 день):**
    *   **Задача:** Сделать простейший одностраничный HTML-файл с `textarea` для ввода сюжета и кнопкой "Анализировать".
    *   **Результат:** После нажатия кнопки под формой должен выводиться результат анализа: список извлеченных сущностей и список найденных "сюжетных дыр".

5.  **Документация и планирование (1 день):**
    *   **Задача:** Кратко задокументировать результаты работы PoC. На основе полученного опыта составить план по интеграции этого функционала в основной проект, включая выбор графовой базы данных (например, Neo4j) для постоянного хранения.


## Задача 1: загрузка сюжета, анализ на "дыры" и дозаполнение
Здесь Графы Знаний — ключевой и абсолютно незаменимый инструмент. Просто LLM здесь не справится, потому что ей не хватает структурированного "понимания" всего сюжета целиком.

Как это будет работать:

### Шаг 1: Извлечение Сущностей и Отношений (Entity & Relationship Extraction)

- Пользователь загружает текст (синопсис, краткий сюжет).
- Мы отправляем этот текст в LLM со специальным промптом. Промпт должен быть примерно таким: "Проанализируй следующий сюжет. Выдели все ключевые сущности: Персонажи, Локации, Предметы, События. Для каждой сущности определи ее атрибуты (например, для Персонажа: 'цель', 'страх', 'внешность'). Затем определи отношения между ними. Выведи результат в формате JSON."
- Пример результата (JSON):
```json
{
  "entities": [
    {"id": "hero", "type": "Character", "name": "Арагорн", "attributes": {"goal": "Защитить Фродо"}},
    {"id": "ring", "type": "Item", "name": "Кольцо Всевластия"},
    {"id": "mordor", "type": "Location", "name": "Мордор"}
  ],
  "relationships": [
    {"from": "hero", "to": "ring", "type": "PROTECTS"},
    {"from": "hero", "to": "mordor", "type": "TRAVELS_TO"}
  ]
}
```

### Шаг 2: Построение Графа Знаний

- Этот JSON — идеальное сырье для графа. Мы берем его и программно строим граф. Каждая "entity" становится узлом (node), а каждое "relationship" — ребром (edge), соединяющим узлы.
- Инструменты: Для начала и прототипа можно использовать библиотеку Python networkx. Для полномасштабного решения — графовую базу данных, например, Neo4j или NebulaGraph.

### Шаг 3: Анализ графа и поиск "дыр" (Вот она, магия!)

- Когда у нас есть граф, мы можем выполнять по нему запросы, чтобы найти логические несостыковки. Это то, что LLM сама по себе сделать не может.
- Примеры "дыр" и как их найти:
  1. "Висячий персонаж": Персонаж, у которого нет или очень мало связей с другими. Запрос к графу: "Найти узлы типа 'Character' с количеством связей < 2".
  2. "Телепортация": Персонаж появляется в сцене в одной локации, а в следующей сцене — в другой, без события "путешествия" между ними. Запрос: "Найти последовательные события для персонажа, где location меняется без ребра TRAVELS_TO".
  3. "Неиспользуемое ружье Чехова": Важный предмет, который вводится, но никогда не используется. Запрос: "Найти узлы типа 'Item' с атрибутом 'important: true', у которых нет связей типа 'IS_USED_IN'".
  4. Противоречия: Персонаж одновременно "ДРУЖИТ" и "НЕНАВИДИТ" другого. Запрос: "Найти пары узлов, соединенные противоречивыми ребрами".

### Шаг 4: Дозаполнение (ручное и автоматическое)

- Найденные "дыры" мы показываем пользователю прямо на графе — это будет очень наглядно.
- Автоматическое дозаполнение: Для найденной дыры (например, "у героя нет мотивации") мы можем снова обратиться к LLM: "Вот часть графа сюжета [передаем контекст]. У персонажа 'X' отсутствует мотивация для события 'Y'. Предложи 3 возможных мотивации."

## Задача 2: разложение готового текста на наши составляющие 
Здесь Графы Знаний — это скорее конечный продукт, а не основной инструмент. Главный инструмент здесь — LLM с продвинутыми техниками промптинга.

Как это будет работать:

Это задача "сверху вниз".

### Шаг 1: Сегментация на Главы (Chapter Segmentation)

- Самый простой шаг. Ищем явные маркеры ("Глава 1", "Chapter X") или, если их нет, просим LLM разбить весь текст на крупные тематические блоки.

### Шаг 2: Сегментация на Сцены (Scene Segmentation)

- Это сложнее. Сцена — это непрерывный блок действия в одном месте в одно время.
- Мы подаем в LLM текст одной главы и просим: "Разбей этот текст на отдельные сцены. Сцена заканчивается, когда происходит скачок во времени или смена локации. Для каждой найденной сцены выведи ее краткое описание, список персонажей и локацию. Ответ дай в JSON."

### Шаг 3: Декомпозиция Сцены на Кадры (Frame Decomposition)

- Это самый сложный и самый творческий шаг. Мы берем текст одной сцены и просим LLM выступить в роли режиссера.
- Промпт: "Представь, что ты снимаешь фильм по этой сцене. Разбей ее на последовательность отдельных 'кадров' или 'планов'. Для каждого кадра дай краткое визуальное описание (что мы видим?) и основной диалог или действие. Каждый 'кадр' должен быть одним статичным моментом или коротким действием."
### Шаг 4 (Опционально): Построение Графа Знаний

- После того как весь текст разложен на структуру "История -> Главы -> Сцены -> Кадры", мы можем запустить по этому структурированному тексту процесс из Задачи 1, чтобы извлечь сущности, построить граф и предложить пользователю найти "дыры" уже в его собственном тексте.
