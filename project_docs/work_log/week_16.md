# Неделя 16: Глубокая отладка и рефакторинг архитектуры

**Дата:** 10.03.2026 - 14.03.2026

На этой неделе была проделана колоссальная работа по стабилизации и рефакторингу ключевых компонентов системы. Мы выявили и устранили несколько глубоких архитектурных проблем, которые приводили к сбоям и непредсказуемому поведению.

### Ключевые достижения:

1.  **Выделение асинхронного воркера.** Изначальная проблема заключалась в том, что API-эндпоинт (`orchestrator`) выполнял "тяжелые" задачи по генерации контента синхронно, что приводило к долгим ответам и возможным тайм-аутам.
    *   **Решение:** Мы разделили бэкенд на два независимых сервиса:
        *   **`Orchestrator`**: Легковесный FastAPI-сервис, чья единственная задача — принимать запросы, валидировать их и ставить задачи в очередь.
        *   **`Worker`**: Celery-воркер, который подхватывает задачи из очереди и выполняет ресурсоемкие операции (вызовы LLM, обработка данных).

2.  **Переход к монорепозиторной структуре.** После разделения сервисов возникла проблема дублирования кода (модели SQLAlchemy, схемы Pydantic, бизнес-логика).
    *   **Решение:** Мы реструктурировали проект, создав общую директорию `common`. Теперь и `orchestrator`, и `worker` импортируют общую логику из `common`, что устраняет дублирование и упрощает поддержку.

3.  **Логическое разделение моделей данных.** Мы осознали, что смешивать быстрые CRUD-операции и медленные операции генерации в одной модели — это ошибка.
    *   **Решение:** Введены две четко разделенные Pydantic-модели:
        *   **`CrudActions`**: Содержит только быстрые операции (delete, update, move).
        *   **`GenerationActions`**: Содержит только медленные операции (generate, regenerate).

4.  **Разработка транзакционного подхода к обработке.** Возникла критическая проблема: как гарантировать, что CRUD-операции (например, удаление) выполнятся *до* того, как задачи на генерацию будут поставлены в очередь?
    *   **Решение:** Мы реализовали гибридную модель в главном API-эндпоинте:
        1.  **Сначала** все действия из `CrudActions` выполняются **синхронно** в рамках одной транзакции базы данных.
        2.  **Только после успешного** выполнения CRUD-операций, задачи из `GenerationActions` ставятся в очередь Celery.

5.  **Внедрение паттерна "Сбор ошибок" (Error Collection).** Первоначальная реализация "падала" на первой же ошибке, не давая пользователю полного представления о всех проблемах в его запросе.
    *   **Решение:** Мы переписали сервис обработки CRUD, внедрив двухфазный подход:
        1.  **Фаза Валидации:** Функция проходит по *всем* запланированным CRUD-действиям, **не внося изменений в БД**, и собирает все потенциальные ошибки (например, "объект не найден") в список.
        2.  **Фаза Выполнения:** Если список ошибок пуст, запускается транзакция для реального выполнения всех действий. Если в списке есть хотя бы одна ошибка, транзакция не начинается, а фронтенду возвращается полный список всех найденных проблем.

6.  **Улучшение обратной связи на уровне API.** API-эндпоинт был доработан для корректной обработки результатов "Сбора ошибок".
    *   **Решение:** Теперь эндпоинт возвращает либо `202 Accepted` в случае успеха, либо `400 Bad Request` с полным JSON-массивом всех ошибок валидации, что позволяет фронтенду отобразить их пользователю за один раз.

7.  **Очистка и рефакторинг базового CRUD-слоя.** Мы заметили, что метод `update` требовал предварительной загрузки объекта.
    *   **Решение:** Метод `update` в `CRUDBase` был переписан. Теперь он принимает `id` объекта, самостоятельно находит его в базе и инкапсулирует логику обработки случая, когда объект не найден.

8.  **Оптимизация TypeScript-типов на фронтенде.** Структуры данных для фронтенда и для отправки на бэкенд сильно дублировались.
    *   **Решение:** Мы использовали дженерики (Generics) в TypeScript, чтобы создать единую базовую структуру `ActionPayload<D, I, R>`. Это позволило нам определить `OrchestrationAction` (для UI) и `BackendActions` (для API) на основе одной и той же "формы", убрав дублирование кода.

9.  **Определение строгого порядка выполнения CRUD-операций.** Для избежания ошибок внешних ключей при удалении связанных сущностей.
    *   **Решение:** В `run_crud_orchestration` был зафиксирован строгий порядок выполнения удалений: от самого вложенного уровня к самому общему (`frame` -> `scene` -> `chapter`).

10. **Создание специализированных Celery-тасков.** Изначально была идея создать отдельные таски для CRUD и генерации.
    *   **Решение:** В ходе обсуждения мы пришли к выводу, что выносить быстрые CRUD-операции в Celery — это излишнее усложнение. В итоге остался только один тип задач `run_generate`, а CRUD-операции выполняются синхронно.

11. **Унификация исполнителя Celery-задач.** Код для запуска `async` функций внутри синхронного Celery-воркера дублировался.
    *   **Решение:** Создана универсальная функция-обертка `_execute_task`, которая управляет `asyncio loop`, сессией базы данных, валидацией Pydantic-моделей и логированием, что сделало код тасков более чистым и DRY (Don't Repeat Yourself).

12. **Обновление API-эндпоинта для использования двухфазного подхода.** Конечная точка была переписана для полной интеграции с новым сервисом `run_crud_orchestration`, который возвращает список ошибок.

13. **Введение структурированной модели ошибок.** Для передачи детальной информации об ошибках на фронтенд была создана Pydantic-модель `ActionError`.

14. **Настройка `docker-compose.yml` для новой структуры.** Файл был обновлен для сборки и запуска трех отдельных сервисов (`orchestrator`, `worker`, `common` как часть других).

15. **Конфигурация Celery.** Созданы файлы `celery_app.py` для `orchestrator` (чтобы знать, куда отправлять) и `worker` (чтобы знать, откуда слушать).

16. **Реализация `_get_eager_loading_options` в `CRUDBase`**. Это позволило гибко настраивать жадную загрузку связанных объектов для разных моделей.

17. **Использование `asyncio.run()` для запуска асинхронного кода из Celery.** Это современный и безопасный способ вместо управления `event loop` вручную.

18. **Переход на `Omit<T, K>` в TypeScript.** Это позволило более декларативно определять типы для бэкенда, исключая ненужные поля.

19. **Добавление `commit=False` в методы CRUD.** Это позволило управлять транзакцией на более высоком уровне, в вызывающем сервисе.

20. **Определение `name` для Celery-тасков.** Это улучшает интроспекцию и позволяет ссылаться на таски по имени, а не по пути к модулю.

21. **Применение `jsonable_encoder` при возврате ошибок.** Это гарантирует, что даже сложные Pydantic-модели будут корректно сериализованы в JSON.

22. **Обсуждение и отказ от `Celery Chains`.** Мы рассмотрели возможность использования `chain` для связи `crud` и `generate` тасков, но пришли к выводу, что гибридная синхронно-асинхронная модель проще и надежнее для нашего случая.

23.  **Решена проблема `Instance has been deleted` в SQLAlchemy:** Устранена коварная ошибка, возникавшая при обновлении родительских сущностей (`Scene`, `Chapter`) после удаления их дочерних элементов. Проблема была в неверном использовании `cascade="all, delete-orphan"`.

24.  **Оптимизированы каскадные операции:** Проведен рефакторинг моделей SQLAlchemy. Логика каскадного удаления была перенесена с уровня ORM на уровень базы данных с помощью `ondelete="CASCADE"`, а в `relationship` оставлена безопасная конфигурация `cascade="save-update, merge"`.

25.  **Внедрена синхронизация состояния с `db.expire()`:** Решена проблема рассинхронизации кэша сессии SQLAlchemy (Identity Map) и реального состояния БД. Теперь после прямых SQL-запросов (например, массового удаления) состояние объекта принудительно обновляется из базы данных.

26.  **Реализована архитектура "Издатель-Подписчик" (Pub/Sub) для Celery и WebSocket:** Полностью переработана система уведомлений. Прямые, неработоспособные вызовы от Celery к вебсокетам заменены на надежную схему с использованием Redis Pub/Sub.

27.  **Celery как "Издатель":** Задачи Celery теперь не пытаются работать с вебсокетами, а публикуют сообщения о результатах своей работы (успех/ошибка) в каналы Redis.

28.  **FastAPI как "Подписчик":** В основное приложение FastAPI добавлен фоновый процесс (`redis_listener`), который подписывается на каналы Redis и работает в течение всего жизненного цикла приложения.

29.  **Интеграция через Lifespan Manager:** Запуск и остановка фонового слушателя Redis элегантно управляется через новый механизм `lifespan` в FastAPI, что гарантирует корректный запуск и завершение.

30.  **Исправлена сериализация Pydantic для Celery:** Устранена ошибка `ValidationError`, возникавшая при передаче сложных Pydantic-моделей в Celery. Внедрен правильный паттерн: `model_dump()` перед отправкой и `model_validate()` в воркере.

31.  **Обеспечена атомарность транзакций:** Проведен рефакторинг CRUD-операций. Убраны `commit()` из низкоуровневых методов, чтобы управление транзакцией (commit/rollback) происходило на верхнем, сервисном уровне.

32. **Исправлена логика `run_crud_orchestration`:** Восстановлена корректная работа функции, отвечающей за выполнение CRUD-операций, в частности, операции `DELETE` теперь выполняются до запуска основной задачи.

33. **Скорректирована конфигурация Docker-Compose:** Исправлены ошибки в `docker-compose.yml`, связанные с монтированием томов и командами запуска `celery_worker`, что устранило ошибки `ModuleNotFoundError`.
