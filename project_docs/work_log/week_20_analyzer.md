Вот мой план, как мы его построим.

Основная идея: Мы создадим многоэтапный, конвейерный процесс (pipeline), в котором разные ИИ-агенты, как команда специалистов, будут последовательно анализировать текст, каждый на своем уровне абстракции. Мы будем активно использовать и графовые, и векторные возможности нашего стека.

Задача: Прежде чем резать текст, мы должны его "понять". Нам нужно превратить плоский текстовый файл в структурированный набор семантических блоков, с которыми сможет работать ИИ.

Действия:

Создание TextChunkerService в analyzer_service:
Этот сервис будет брать на вход большой текст.
Он не будет просто делить его по абзацам. Он будет использовать рекурсивный алгоритм чанкинга с учетом семантики. Текст будет разбиваться на небольшие, слегка перекрывающиеся фрагменты (чанки) фиксированного размера в токенах. Это создаст "контекстные окна", идеальные для анализа.
Векторизация и Индексация в ChromaDB:
Каждый чанк немедленно векторизуется и загружается во временную, изолированную коллекцию в ChromaDB. В метаданных каждого чанка будут храниться его порядковый номер и исходный текст.
Зачем это нужно? Теперь у нас есть "карта" всего текста в векторном пространстве. Мы можем выполнять семантический поиск, находить тематические кластеры и, что самое важное, определять резкие смены темы, которые часто являются границами сцен.
Результат Фазы 1: Вместо одного .txt файла у нас есть интерактивная, семантическая карта текста в ChromaDB. Фундамент заложен.

Задача: Найти самые базовые строительные блоки истории — Сцены. Сцена — это непрерывный отрезок действия в одном месте, в одно время, с одной группой персонажей.

Действия:

Создание SceneDetectionAgent в analyzer_service:
Этот агент не читает текст линейно. Он "скользит" по семантической карте, которую мы создали в Фазе 1.
Как он работает: Агент берет чанк N и сравнивает его по семантической близости с чанком N+1, N+2 и т.д.
Ключевая технология: Как только семантическое расстояние (cosine distance) между чанками резко увеличивается, агент понимает: "Произошел разрыв! Сменилась локация, время или состав персонажей". Это — вероятный конец одной сцены и начало другой.
Интеллектуальная Валидация:
Обнаружив такой "разрыв", агент не просто режет текст. Он отправляет "пограничные" чанки (два до разрыва и два после) в LLM с промптом:
"Это конец одной сцены и начало другой? Обоснуй свой ответ, указав на смену локации, времени или действующих лиц. Предложи краткое название и однострочное описание для новой сцены."

Формирование Объектов Сцен:
Агент собирает ответы LLM. Каждый положительный ответ порождает временный объект Scene с названием, описанием и списком ID чанков, которые в него входят.
Результат Фазы 2: У нас есть плоский список идентифицированных и описанных сцен, из которых состоит вся история. Мы декомпозировали текст на его атомарные нарративные единицы.

Задача: Сгруппировать атомарные сцены в более крупные структуры — Главы и Арки.

Действия:

Создание StructureComposerAgent:
Этот агент получает на вход список объектов Scene из предыдущей фазы.
Группировка в Главы: Агент снова использует LLM, но на более высоком уровне. Он передает ему только названия и описания сцен:
"Вот последовательный список сцен. Сгруппируй их в логические главы. Для каждой главы предложи название и краткое резюме. В ответе дай только структуру: [ { 'chapter_title': '...', 'summary': '...', 'scene_indices': [1, 2, 3] }, ... ]"

Группировка в Арки: Агент повторяет процесс, но теперь для глав:
"Вот список глав. Сгруппируй их в 3-5 крупных сюжетных арок (завязка, развитие, кульминация, развязка). Для каждой арки предложи название и опиши ее ключевую цель в сюжете. Ответ дай в виде структуры..."

Результат Фазы 3: У нас есть полная иерархическая структура всей книги в виде вложенных объектов: Арки, содержащие Главы, содержащие Сцены. Это и есть результат работы "ИИ-Архитектора".

Задача: Превратить абстрактную структуру в конкретные узлы и связи в наших базах данных (Postgres + Neo4j).

Действия:

Создание GraphAssemblerService:
Этот сервис получает иерархическую структуру от "Компоновщика".
Он начинает рекурсивный обход "сверху-вниз":
Создает узлы для Арок.
Для каждой Арки создает узлы для Глав и связывает их связью CONTAINS.
Для каждой Главы создает узлы для Сцен и связывает их.
Для каждой Сцены он объединяет текст из ее чанков и сохраняет его в поле description.
Переиспользование кода: Этот сервис будет активно использовать уже существующие у нас CRUD-менеджеры и, возможно, метод _create_and_save_object из BaseOrchestrationService, чтобы создавать узлы в Postgres и Neo4j одновременно.
Конечный результат: Пользователь загружает один .txt файл, а через несколько минут в его проекте появляется полная, структурированная иерархия истории, готовая к дальнейшей работе — генерации изображений, уточнению деталей и т.д.

Этот план амбициозен, технологичен и полностью соответствует вашему запросу на "более качественный подход". Он превращает analyzer_service из простого парсера в настоящий центр интеллектуальной обработки нарратива.
