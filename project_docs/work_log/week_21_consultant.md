# План реализации Open Source ИИ API Ассистента

Этот документ описывает шаги для создания нового, независимого сервиса "ИИ Ассистент", который будет предоставлять API для бэкенда, уметь отвечать на вопросы и вызывать внешние функции.

## Шаг 1: Создание структуры проекта и базового API

**Цель:** Подготовить "скелет" нашего нового сервиса и убедиться, что он может общаться с основным бэкендом.

1.  **Создать новую директорию:** В корне проекта создадим папку `ai_assistant_service`.
2.  **Настроить окружение:** Внутри `ai_assistant_service` создадим `pyproject.toml` для управления зависимостями. Основные библиотеки: `fastapi`, `uvicorn`, `httpx`.
3.  **Создать API-endpoint:** Реализуем простой API с помощью FastAPI (`main.py`). Он будет иметь одну точку входа, например, `/api/v1/chat`.
4.  **Docker-интеграция:**
    *   Создадим `Dockerfile` для нового сервиса.
    *   Обновим `docker-compose.yml`, добавив `ai_assistant_service`, чтобы он запускался вместе со всей системой.

**Результат:** Рабочий, но "пустой" сервис, который принимает запросы от бэкенда.

## Шаг 2: Реализация логики Оркестратора

**Цель:** Научить сервис понимать намерение пользователя и решать, что делать: ответить самому или вызвать инструмент.

1.  **"Сердце" Ассистента:** Внутри сервиса создадим класс или модуль `Orchestrator`.
2.  **Основной цикл:** При получении запроса на `/chat`, `Orchestrator` будет:
    *   Принимать текст пользователя и историю диалога.
    *   Обращаться к LLM (на этом этапе можно использовать заглушку или реальную модель) с системным промптом, описывающим его роль.
    *   Анализировать ответ модели: это просто текст или команда на вызов функции?

## Шаг 3: Определение и вызов "инструментов" (заглушки API)

**Цель:** Дать ассистенту возможность выполнять действия.

1.  **Реестр инструментов:** Создадим модуль `tools`, где определим наши функции-заглушки. Например:
    *   `get_project_status()` -> возвращает "Проект в активной фазе разработки".
    *   `get_user_info(user_id: int)` -> возвращает "Пользователь с ID {user_id} - администратор".
2.  **Описание инструментов для LLM:** Создадим механизм, который будет передавать LLM описания этих функций в формате, который она понимает (например, JSON Schema).
3.  **Механизм вызова:** Если `Orchestrator` получает от LLM команду вызвать инструмент (например, `get_project_status`), он должен:
    *   Найти эту функцию в реестре `tools`.
    *   Выполнить её.
    *   Отправить результат обратно в LLM, чтобы она сформулировала финальный ответ для пользователя.

**Результат:** Ассистент, который может не только говорить, но и "действовать", вызывая внутренние функции-заглушки.

## Шаг 4: Интеграция с реальным API

**Цель:** Заменить заглушки на вызовы реальных внешних или внутренних сервисов.

1.  **Обновление инструментов:** Модифицируем функции в `tools`. Теперь они будут не просто возвращать строку, а делать реальный HTTP-запрос (например, к нашему основному `backend`) с помощью `httpx`.
2.  **Обработка ошибок и асинхронность:** Улучшим вызовы, добавив обработку ошибок сети, таймаутов и используя асинхронные вызовы для повышения производительности.

**Итог:** Мы получим полноценный, расширяемый сервис ИИ-ассистента, который изолирован от основной логики бэкенда, легко масштабируется и может быть обогащен новыми "инструментами" для выполнения любых задач.
