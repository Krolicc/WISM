# Архитектурный План: Атомизация Информации о Сущностях

## Исходная Проблема

Текущий подход к управлению сущностями основан на сложной и хрупкой системе "консолидации". Он требует от LLM "сливать" новые описания с существующими "каноническими" описаниями.

**Минусы этого подхода:**
1.  **Сложность:** Требуется многоступенчатый процесс (Извлечь -> Сравнить -> Создать План -> Выполнить План). Код для `ConsolidationPlan`, `MERGE`, `IGNORE` является сложным и трудноподдерживаемым.
2.  **Необратимость:** Если фрагмент текста, послуживший источником части описания, удаляется, нет простого способа "откатить" изменения в "слитом" каноническом описании.
3.  **Непредсказуемость:** Результат слияния зависит от LLM и может быть нестабильным. Важные детали могут быть утеряны или искажены.
4.  **Производительность:** Множественные вызовы LLM для слияния являются медленными и дорогостоящими.

## Новое Решение: "Атомизация Фрагментов"

Мы кардинально меняем подход, полностью отказываясь от концепции "слияния". Вместо этого мы разделяем **идентичность** сущности от **информации** о ней.

1.  **Сущность (`Entity`)** - это просто идентификатор и имя (например, "Шерлок Холмс").
2.  **Фрагмент Описания (`EntityDescriptionFragment`)** - это новая концепция. Каждая крупица информации о сущности хранится как отдельная, "атомарная" запись в новой таблице в **PostgreSQL**.

### Новая Схема Данных

Мы создадим новую таблицу `entity_description_fragments` в **PostgreSQL**.

**Структура таблицы:**
*   `id` (PK, UUID): Уникальный идентификатор самого фрагмента.
*   `entity_id` (FK, UUID): Внешний ключ, указывающий на сущность в таблице `entities`.
*   `fragment_text` (TEXT): Сам текст фрагмента (например, "играет на скрипке").
*   `source_node_id` (INTEGER): **Числовой ID узла из Neo4j** (например, `:Scene`, `:Chapter`). Это *не* внешний ключ, а просто "указатель" на источник информации в графе.
*   `value_score` (INTEGER): Оценка важности фрагмента (1-10), присваиваемая LLM.

**Важно:** Мы **не** создаем новые узлы для фрагментов в Neo4j. Графовая база данных используется только для хранения структуры истории и связей, а PostgreSQL — для хранения контента.

### Новый Рабочий Процесс

Старый сложный процесс полностью заменяется новым, элегантным:

1.  **Извлечь:** Из текста (например, из `Scene` с ID `12345` в Neo4j) извлекаются новые фрагменты информации.
2.  **Идентифицировать:** Определяется, к какой существующей или новой сущности относится каждый фрагмент.
3.  **Сохранить:** Каждый новый фрагмент просто добавляется как **новая строка** в таблицу `entity_description_fragments` в PostgreSQL, с указанием `source_node_id = 12345`.

### Генерация Описаний "На Лету"

Когда требуется полное описание сущности:
1.  Собираются все `fragment_text` из таблицы `entity_description_fragments` для данного `entity_id`.
2.  Они передаются в LLM с простым промптом: `"Сведи эти факты в связный абзац"`.
3.  Результат кэшируется в поле `description` таблицы `entities`, а флаг `is_description_stale` (новое поле в `entities`) устанавливается в `False`.

### Преимущества Новой Архитектуры

*   **Простота:** Весь сложный код для консолидации и слияния удаляется.
*   **Обратимость:** При удалении узла-источника из Neo4j (например, `Scene`), мы можем легко удалить все связанные с ним фрагменты из PostgreSQL по `source_node_id`, и описание автоматически обновится при следующей генерации.
*   **Производительность и Стоимость:** Мы заменяем множество дорогих операций слияния на простые и быстрые вставки в базу данных.
*   **Масштабируемость:** Система легко расширяется и не зависит от жесткой иерархии в схеме PostgreSQL.

Я предлагаю следующую структуру для нашей новой таблицы EntityDescriptionFragment:

entity_id: (FK) UUID сущности, к которой относится фрагмент.
source_node_id: Числовой ID узла из Neo4j. Это поле напрямую связывает фрагмент с его источником в графе.
fragment_text: Текст самого фрагмента.

Почему это решение на порядок лучше:

Абсолютная гибкость: Нам неважно, является ли source_node_id ссылкой на :Frame, :Scene или даже на узел нового типа, который мы добавим в будущем. Схема базы данных не меняется.
Единственный источник правды: Структура истории живет в Neo4j. Мы просто ссылаемся на нее, не дублируя иерархию в PostgreSQL.
Простое удаление: Когда узел в Neo4j (например, Frame с id 12345) удаляется, мы можем запустить фоновую задачу, которая выполнит простой запрос: DELETE FROM entity_description_fragments WHERE source_node_id = 12345.
Это делает наши базы данных идеально дополняющими друг друга:

PostgreSQL: Хранит "атомарные" данные и контент.
Neo4j: Хранит связи и иерархию.
