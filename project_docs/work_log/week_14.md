## Проделанная работа

Дата: 03-04.03.2026

### 1. Анализ и постановка проблемы

Изначальная архитектура сервисов(`ChapterService`, `SceneService` и т.д.) страдала от значительного дублирования кода. Сложная логика для генерации контента, взаимодействия с LLM и управления иерархией была скопирована в каждом сервисном классе. Это делало поддержку и расширение системы крайне затруднительными.

Тоже самое и ниже касается и  crud файлов: как базового, так и наследников.

### 2. Рефакторинг сервисного слоя: `BaseOrchestrationService`

Для решения этой проблемы был создан абстрактный базовый класс `BaseOrchestrationService`.

- **Универсальная логика**: В этот класс была вынесена вся общая логика, включая:
  - Рекурсивную генерацию контента (`regenerate_content`).
  - Рекурсивное создание соседних элементов с умным упорядочиванием (`generate_and_save_adjacent`).
  - Взаимодействие со схемами Pydantic и моделями LLM.
- **Декларативный подход**: Классы-наследники теперь не содержат логики, а лишь *декларируют* свою роль в системе через `@property`:
  - `model_name`: Название модели ("chapter", "scene").
  - `crud_manager`: Менеджер CRUD для этой модели.
  - `llm_schema`: Схема для парсинга ответа от LLM.
  - `parent_id_field_name`: Название поля для связи с родителем.
  - `child_service`: Ссылка на сервис дочернего уровня.

### 3. Создание "Тонких" сервисов

Все существующие сервисы были переписаны как наследники `BaseOrchestrationService`. В результате файлы `story_service.py`, `chapter_service.py`, `scene_service.py` и `frame_service.py` стали невероятно компактными и читаемыми, полностью избавившись от бизнес-логики.

### 4. Создание Сервиса-Оркестратора (`orchestration_service.py`)

Это стало кульминацией рефакторинга. Был создан `orchestration_service.py`, который выступает в роли центрального дирижера для всех операций.

- **Управление по Действиям (Action-Driven)**: Сервис принимает на вход список *действий* (actions), например: `{"action_type": "create", "level": "chapter", "params": {...}}`.
- **Карта Уровней**: Внутренний словарь сопоставляет уровни ("story", "chapter", "scene", "frame") с соответствующими "тонкими" сервисными объектами.
- **Динамический Вызов**: Оркестратор динамически находит и вызывает нужный метод на нужном сервисе (или его CRUD-менеджере) в зависимости от `action_type`.
- **Передача Контекста**: Реализован механизм для передачи результатов одного шага в качестве параметров для следующего (например, `id` созданной главы используется для создания сцены в ней). Это позволяет строить сложные цепочки команд.

### 5. Интеграция с WebSocket

В сервис-оркестратор была добавлена критически важная функциональность, вдохновленная предыдущими версиями: отправка уведомлений через WebSocket. После выполнения действия (например, регенерации сцены), оркестратор отправляет клиенту обновленный родительский объект (всю главу), обеспечивая интерактивность и актуальность данных на фронтенде.

### 6. Перенос в фоновые задачи Celery

Наконец, для повышения отзывчивости API, вся логика оркестрации была обернута в фоновую задачу Celery. Был создан файл `worker/tasks.py`, содержащий задачу `run_orchestration_task`.

- **Быстрый API**: Теперь API-эндпоинт не ждет завершения всей (потенциально долгой) цепочки генерации, а немедленно принимает запрос, передает его в Celery и возвращает ответ пользователю.
- **Изоляция**: Задача выполняется в отдельном процессе воркера, управляя собственной сессией базы данных.
