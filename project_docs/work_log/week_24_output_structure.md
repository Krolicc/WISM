'''
# Визуализация ветвлений в структуре повествования

Этот документ описывает логические правила и сценарии ветвления сюжета, которые должны быть учтены при разработке пользовательского интерфейса, в частности `TimelineView`.

## 1. Основные принципы

1.  **Строгая иерархия уровней**: Ветвления и последовательности могут существовать только между узлами **одного и того же типа (уровня)**. Например, арка может ветвиться на другие арки, но не может напрямую вести к главе или сцене. Переход между уровнями осуществляется исключительно через действия пользователя (например, двойной клик для "проваливания" внутрь узла).

2.  **Два типа связей**:
    *   **`CONTAINS` (Содержит)**: Вертикальная связь "родитель-ребенок". Определяет принадлежность. Например, `Story` содержит `Arc`, а `Chapter` содержит `Scene`. Родительский узел содержит **все** дочерние узлы, независимо от их внутренней структуры.
    *   **`NEXT` (Следующий)**: Горизонтальная связь "пир-пир". Определяет последовательность и ветвление. Именно этот тип связи мы визуализируем на таймлайне.

---

## 2. Типовые сценарии ветвления на одном уровне

Рассмотрим на примере уровня "Арки" внутри одной "Истории". `Story` в данном случае является родительским контейнером.

### А. Простая последовательность (1-в-1)

Самый базовый сценарий. Одна арка ведет к другой.

- **Структура**: `[Арка A] -> [Арка B] -> [Арка C]`
- **Связи `NEXT`**: (`A` -> `B`), (`B` -> `C`)
- **Связи `CONTAINS`**: Родитель (`Story`) содержит A, B, и C.

### Б. Расширение (1-в-N)

Одна арка является точкой, из которой сюжет разветвляется на несколько параллельных путей.

- **Структура**:
  ```
       / -> [Арка B]
  [Арка A] 
       \ -> [Арка C]
  ```
- **Связи `NEXT`**: (`A` -> `B`), (`A` -> `C`)
- **Связи `CONTAINS`**: Родитель (`Story`) содержит A, B, и C. Наличие нескольких исходящих `NEXT`-связей из узла А и определяет ветвление.

### В. Сужение (N-в-1)

Несколько сюжетных веток сходятся в одной ключевой точке.

- **Структура**:
  ```
  [Арка B] -> \
              [Арка A]
  [Арка C] -> /
  ```
- **Связи `NEXT`**: (`B` -> `A`), (`C` -> `A`)
- **Связи `CONTAINS`**: Родитель (`Story`) содержит A, B, и C. Наличие нескольких входящих `NEXT`-связей в узел А определяет слияние.

### Г. Параллельные независимые ветки

Это ответ на вопрос: "можем ли мы два ветвления держать в одной главе?". **Да, можем.**

Это сценарий, когда внутри одного контейнера (например, `Chapter`) существуют две или более независимые последовательности (например, `Scene`).

- **Структура в рамках одной Главы**:
  - Ветка 1: `[Сцена 1.1] -> [Сцена 1.2]`
  - Ветка 2: `[Сцена 2.1] -> [Сцена 2.2]`
- **Связи `NEXT`**: (`1.1` -> `1.2`), (`2.1` -> `2.2`). **Важно**: между этими двумя ветками нет `NEXT`-связей.
- **Связи `CONTAINS`**: Родитель (`Chapter`) содержит все четыре сцены: `1.1, 1.2, 2.1, 2.2`.
- **Как это работает?**: При "входе" в главу, мы ищем узлы, у которых нет входящих `NEXT`-связей *от узлов из этого же контейнера*. В данном примере это `Сцена 1.1` и `Сцена 2.1`. Они и являются отправными точками для двух параллельных дорожек на таймлайне.

---

## 3. Выводы для реализации

1.  **Родитель всегда содержит всё**. Логика отображения не должна беспокоиться о том, как получить дочерние узлы. Она должна запросить у `contentStore` всех детей для активного родителя (например, все арки для `activeStoryId`).

2.  **Ветвление определяется связями `NEXT`**. Вся логика построения таймлайна, определения дорожек и порядка должна базироваться исключительно на анализе `NEXT`-связей между узлами одного уровня.

3.  **Изолированность уровней — закон**. Никаких "перекрестных" ссылок между уровнями в `TimelineView` быть не должно. Это сохранит интерфейс чистым и предсказуемым.

---

## 4. Проблема "Неосведомленного Родителя"

Как отмечено в пункте 3.1, родитель просто содержит набор дочерних узлов. Он "не знает", представляют ли эти дети простую линейную последовательность или сложную ветвящуюся структуру. Вся работа по определению этой структуры ложится на клиентский код (UI), который должен каждый раз анализировать все дочерние узлы и их `NEXT`-связи.

Это создает несколько проблем:

-   **Сложность UI**: Логика `TimelineView` усложняется, так как ей приходится быть "умной" и реконструировать структуру графа на лету.
-   **Неявный замысел**: Структура данных не отражает явно замысел автора. "Эта группа сцен является ветвлением" — это вывод, а не факт, заложенный в данных.
-   **Хрупкость**: Любые изменения в логике `NEXT`-связей могут привести к неожиданному и неверному отображению, так как нет "якоря", который бы четко группировал узлы, принадлежащие одному ветвлению.

## 5. Предложение: Введение узла-контейнера для ветвлений

Для решения проблемы "неосведомленного родителя" предлагается ввести новый, чисто структурный тип узла. Назовем его **`BranchSet`** (Набор веток) или **`SubNode Branch`**.

Это не узел с контентом (как `Scene`), а мета-узел, единственная задача которого — группировать другие узлы, составляющие единое ветвление.

**Как это будет работать:**

1.  Родитель (например, `Chapter`) больше не содержит напрямую все `Scene`, если они ветвятся.
2.  Вместо этого `Chapter` будет содержать узел `BranchSet`.
3.  Узел `BranchSet`, в свою очередь, будет содержать все `Scene`, которые участвуют в ветвлении.
4.  `NEXT`-связи, как и прежде, будут существовать между узлами `Scene`.

**Визуализация структуры:**

```
[Chapter]
   | (CONTAINS)
[BranchSet]
   | (CONTAINS)
   +-- [Scene A] --(NEXT)--> [Scene B]
   |
   | (CONTAINS)
   +-- [Scene C] --(NEXT)--> [Scene B]
```

Такой подход позволяет явно выделить **краткосрочные выборы** и ветвления внутри одного логического блока (главы, арки), не создавая для этого полноценные новые `Chapter` или `Arc`. Это идеально подходит для сценария "сцена разошлась на две и почти сразу соединилась в одну".

## 6. Плюсы и минусы усложнения структуры

Введение `BranchSet` — это значительное усложнение модели данных. Рассмотрим его последствия.

### Плюсы

1.  **Явный замысел автора**: Структура данных становится самодокументируемой. `BranchSet` четко говорит: "Все, что внутри меня — это единый блок ветвления".
2.  **Резкое упрощение логики UI**: `TimelineView` больше не нужно быть умным. Увидев узел `BranchSet`, компонент просто знает, что ему нужно активировать режим отображения веток для дочерних элементов этого узла. Задача сводится от "обнаружить и проанализировать" к "отобразить по инструкции".
3.  **Инкапсуляция сложности**: Сложность ветвления изолирована внутри `BranchSet`. Родительский узел может иметь простую линейную последовательность из других узлов и `BranchSet`'ов: `[Scene A] -> [BranchSet 1] -> [Scene B]`.
4.  **Масштабируемость**: Модель позволяет легко добавлять новые типы ветвлений в будущем, не ломая базовую логику.

### Минусы

1.  **Усложнение модели данных**: Мы добавляем новый тип узла, который необходимо поддерживать на бэкенде и клиенте.
2.  **Увеличение количества узлов**: Общее число узлов в графе возрастет, что может незначительно повлиять на производительность запросов.
3.  **Потенциальная избыточность**: Нужно определить четкие правила, когда использовать `BranchSet`. Если использовать его для простых линейных последовательностей, это станет избыточным усложнением. **Правило:** `BranchSet` создается только тогда, когда внутри родителя появляется хотя бы одно ветвление (1-в-N) или слияние (N-в-1).
4.  **Более глубокая вложенность**: Путь от `Chapter` к `Scene` теперь может проходить через `BranchSet`, что может потребовать корректировки логики запросов и навигации.

## 7. Технический анализ и влияние на Neo4j

Рассмотрим подход с `BranchSet` с точки зрения производительности и нагрузки на базу данных Neo4j.

### Производительность запросов (Query Performance)

На первый взгляд, добавление узлов `BranchSet` увеличивает общее количество узлов в графе. Однако для графовой СУБД это **не является проблемой, а скорее преимуществом**.

*   **Без `BranchSet` ("Умный UI")**: Чтобы отобразить таймлайн главы, бэкенду пришлось бы выполнить тяжелый запрос: найти главу, найти **всех** ее дочерних сцен, найти **все** `NEXT`-связи между ними, и вернуть все это клиенту. Клиент затем должен выполнить сложный алгоритм, чтобы рассортировать этот клубок связей. Это один большой, медленный запрос и тяжелая обработка на клиенте.

*   **С `BranchSet`**: Запрос для отображения таймлайна главы становится элементарным и **чрезвычайно быстрым**:
    ```cypher
    // Найти все дочерние элементы 1-го уровня для данной главы
    MATCH (c:Chapter {id: $chapterId})-[:CONTAINS]->(child)
    RETURN child
    ```
    Этот запрос мгновенно вернет упорядоченный список, состоящий из узлов `Scene` и `BranchSet`. Он не углубляется в структуру веток, что делает его очень легковесным. Если UI встречает `BranchSet`, он может сделать **второй, отдельный, такой же быстрый запрос** для получения содержимого именно этой ветки. Этот паттерн "множество мелких, быстрых запросов" намного эффективнее для интерактивных интерфейсов, чем один большой и медленный.

### Сложность для Neo4j и гибкость модели

Вопрос: *"Насколько сильно труднее будет для Neo4j, если `BranchSet` появится на любом уровне?"*

Ответ: **Нисколько не труднее. Наоборот, проще и естественнее для графовой модели.**

Neo4j оперирует метками (labels) и связями. Добавление новой метки `BranchSet` — тривиальная операция. Самое главное — **шаблоны запросов остаются идентичными** независимо от уровня вложенности.

Сравните:
*   **Запрос для таймлайна Арки:**
    `MATCH (a:Arc {id: $arcId})-[:CONTAINS]->(child) RETURN child`
    *(Вернет узлы `Chapter` и `BranchSet`)*

*   **Запрос для таймлайна Главы:**
    `MATCH (c:Chapter {id: $chapterId})-[:CONTAINS]->(child) RETURN child`
    *(Вернет узлы `Scene` и `BranchSet`)*

*   **Запрос для содержимого ветки:**
    `MATCH (bs:BranchSet {id: $branchSetId})-[:CONTAINS]->(child) RETURN child`
    *(Вернет узлы, составляющие ветку, например, `Scene`)*

Как видно, **логика для бэкенда абсолютно одинакова**. Ему не нужно знать, на каком уровне он находится. Он просто выполняет один и тот же паттерн `(parent)-[:CONTAINS]->(child)`. Это делает код на бэкенде более простым, надежным и легким в поддержке.

### Выводы по технической составляющей

| Аспект | Подход с `BranchSet` | Альтернативы ("Умный UI") |
| :--- | :--- | :--- |
| **Производительность** | **Высокая.** Множество мелких, индексированных запросов. Нагрузка на БД минимальна. | **Низкая.** Один большой, тяжелый запрос со сложной логикой `MATCH` и большая нагрузка на клиент. |
| **Сложность запросов (Cypher)** | **Низкая.** Простые, декларативные запросы по одному шаблону. | **Высокая.** Сложные, процедурные запросы для выявления неявных структур. |
| **Надежность данных** | **Высокая.** Структура явно определена в базе. | **Низкая.** Зависимость от хрупкой логики на клиенте. |
| **Поддержка и развитие** | **Просто.** Легко добавлять новые свойства и логику. | **Сложно.** Любое изменение требует переписывания сложного алгоритма. |

**Итог:** С точки зрения Neo4j и общей архитектуры бэкенда, введение `BranchSet` — это **однозначное улучшение**. Этот подход лучше соответствует парадигме графовых баз данных, повышает производительность и надежность, а также радикально упрощает код как на бэкенде, так и на фронтенде.

## 8. Взаимодействие Frontend и Backend: Запросы и Упорядочивание

Здесь мы отвечаем на ключевой вопрос: *"Если бэкенд отдает только часть данных, не придется ли фронтенду самому искать всю цепочку?"*

Ответ: **Нет. Фронтенд никогда не "ищет" узлы. Он только отображает небольшие, заранее упорядоченные списки, которые ему предоставляет бэкенд.**

### Преимущество №1: Frontend ленив и глуп (и это хорошо)

Представим, что пользователь кликает на "Главу 1".

1.  **Frontend делает один простой запрос:** `GET /api/nodes/chapter-1/children`.
2.  **Backend выполняет всю работу:** Он находит дочерние элементы первого уровня для `chapter-1`.
3.  **Backend упорядочивает результат:** Это самый важный шаг. Бэкенд, используя `NEXT`-связи, выстраивает эти дочерние элементы в правильном повествовательном порядке.
4.  **Backend возвращает УПОРЯДОЧЕННЫЙ массив:** `[ {id: 'scene-A'}, {id: 'scene-B'}, {id: 'branch-set-1'}, {id: 'scene-E'} ]`.
5.  **Frontend просто отображает этот массив в цикле `v-for`**. Ему не нужно ничего знать о связях, о том, что идет после `scene-B`, или что внутри `branch-set-1`. Он просто рендерит то, что получил, в том порядке, в котором получил. Это быстро, дешево и надежно.

Если пользователь захочет увидеть содержимое `branch-set-1`, он кликнет на него, и frontend сделает **новый** запрос `GET /api/nodes/branch-set-1/children`, снова получая маленький, упорядоченный список для отображения.

### Преимущество №2: Бэкенд занимается упорядочиванием (его работа)

Вопрос: *"Каким образом происходит упорядочивание на бэкенде?"*

Это стандартная задача для графовых баз данных. Бэкенд выполняет алгоритм, похожий на этот:

1.  Находит всех детей родителя: `MATCH (parent)-[:CONTAINS]->(child) ...`
2.  Среди этих детей находит **стартовый узел** (или несколько, для параллельных веток). Это узел, в который не входит `NEXT`-связь от другого ребенка из этой же группы.
3.  От стартового узла начинает **обход графа в ширину или в глубину** по `NEXT`-связям, собирая узлы в массив в порядке их посещения.

Этот обход графа — **чрезвычайно быстрая операция для Neo4j**, выполняемая на сервере, который для этого оптимизирован. В результате этой ОДНОЙ операции на бэкенде мы получаем готовый к отображению, упорядоченный список.

**ИТОГ:** Вместо того чтобы заставлять frontend быть "детективом", который распутывает сложный граф, мы позволяем ему быть простым "визуализатором". А всю "детективную" работу по обходу графа выполняет бэкенд, который создан именно для этого. Это классическое и правильное разделение ответственности, которое ведет к производительному и надежному приложению.

## 9. Загрузка больших уровней: Концепция "Магистрального Сюжета" и Пагинация

Это решение для проблемы уровней с сотнями или тысячами узлов. Нельзя загружать их все сразу. Мы должны показывать только самую важную информацию, подгружая остальное по требованию.

### Концепция "Магистрального сюжета"

При запросе содержимого большого уровня (например, Арки), мы не возвращаем все существующие в ней Главы. Вместо этого, мы возвращаем **только одну, самую важную, повествовательную цепочку** — "магистральный сюжет".

**Как это работает на практике:**

1.  **Определение "магистрали" на бэкенде:** При запросе `GET /api/nodes/arc-1/children?limit=50` бэкенд должен определить "главную" ветку сюжета. Критерии могут быть разными (и их можно комбинировать):
    *   **Явный флаг от автора:** У узла или `BranchSet` может быть свойство `is_main_branch: true`.
    *   **Эвристика "самого длинного пути":** Бэкенд может автоматически рассчитать самую длинную последовательность `NEXT`-связей.
    *   **По умолчанию:** Первая созданная ветка.

2.  **Пагинированный ответ:** Бэкенд проходит по найденной "магистральной" ветке и возвращает первые `N` (например, 50) узлов из этой цепочки. **Важно:** если на пути встречается `BranchSet`, он возвращается как один элемент, но к нему добавляются метаданные.

3.  **Отображение на фронтенде:**
    *   Frontend получает и отображает **одну линейную цепочку** из 50 узлов. Это быстро и просто.
    *   Если узел в этой цепочке был точкой ветвления (за ним следовал `BranchSet`), бэкенд добавляет в его объект специальное поле: `branch_info: { has_branches: true, total: 3 }`.
    *   UI, видя это поле, рисует рядом с узлом иконку (например, `...` или значок ветвления), которая показывает: "Здесь есть еще 2 неисследованные ветки".

### Взаимодействие при выборе другой ветки

Что происходит, когда пользователь кликает на иконку `...`?

1.  UI показывает всплывающее окно или панель со списком альтернативных веток, которые бэкенд может отдать по запросу `GET /api/nodes/branch-set-X/children`.
2.  Пользователь выбирает: "Показать ветку Б".
3.  **Frontend делает НОВЫЙ запрос:** `GET /api/nodes/arc-1/children?limit=50&start_node=node-in-branch-B`.
4.  **Бэкенд повторяет логику:** Теперь он строит "магистральный сюжет", но уже начиная с указанного узла `node-in-branch-B`.
5.  Frontend получает новый упорядоченный список из 50 узлов и заменяет им старый, создавая у пользователя ощущение "переключения" на другую временную линию.

### Выводы

Этот подход сочетает в себе лучшее из двух миров:

*   **Для пользователя:** Возможность видеть общую канву сюжета без перегрузки деталями и плавно "переключаться" на исследование побочных веток.
*   **Для разработчика:** Высокая производительность (загружаем только малые порции данных), простая логика на фронтенде (всегда отображаем один линейный список), и вся сложная работа по навигации по графу инкапсулирована на бэкенде, где ей и место.

## 10. Загрузка данных и Кэширование на клиенте

Этот раздел объединяет концепции "магистрального сюжета" и производительности, описывая конкретную реализацию на стороне клиента.

### Принцип работы

1.  **Изолированный контекст:** Вместо попытки отобразить "бесконечный" таймлайн, UI всегда показывает дочерние узлы **только одного родителя**. Контекст ясен: `Хлебные крошки: Story > Arc > Chapter`. На экране в данный момент — только сцены, принадлежащие этой главе.

2.  **Централизованный кэш:** Вся логика загрузки и кэширования инкапсулируется в `contentStore` (Pinia).

### Реализация в `contentStore`

1.  **Хранилище кэша:**
    В `state` добавляется `Map`:
    `nodeChildrenCache: new Map<string, StoryNode[]>()`
    -   `key`: `id` родительского узла.
    -   `value`: Упорядоченный массив его дочерних узлов.

2.  **"Умный" Action для получения данных:**
    Создается единый `action`, например, `async fetchChildren(nodeId: string)`. Все компоненты вызывают только его.
    -   **Шаг 1: Проверка кэша.** `if (this.nodeChildrenCache.has(nodeId)) return this.nodeChildrenCache.get(nodeId);`
    -   **Шаг 2: Запрос к API.** Если в кэше пусто, `action` выполняет запрос к бэкенду (например, `GET /api/nodes/${nodeId}/children?limit=50`).
    -   **Шаг 3: Сохранение в кэш.** После получения ответа, результат сохраняется: `this.nodeChildrenCache.set(nodeId, response.data);`
    -   **Шаг 4: Возврат данных.**

3.  **Инвалидация (очистка) кэша:**
    Когда пользователь изменяет структуру (добавляет/удаляет узел), необходимо сделать данные в кэше недействительными, чтобы при следующем заходе они были запрошены заново. `orchestrationStore` после успешного коммита изменений на бэкенд вызывает метод `contentStore.invalidateCache(parentNodeId)`, который просто выполняет `this.nodeChildrenCache.delete(parentNodeId);`

### Пользовательский сценарий

1.  Пользователь на уровне Арк. Кликает на `Главу 5`.
2.  `TimelineView` вызывает `contentStore.fetchChildren('chapter-5')`.
3.  Кэш пуст. Идет запрос к API. Получаем `[Scene A, Scene B, ...]`. Данные сохраняются в кэш. `TimelineView` их отображает.
4.  Пользователь возвращается на уровень Арк (данные для этого уровня уже в кэше, все происходит мгновенно).
5.  Пользователь снова кликает на `Главу 5`.
6.  `TimelineView` снова вызывает `contentStore.fetchChildren('chapter-5')`.
7.  `fetchChildren` находит данные в `nodeChildrenCache` и **мгновенно** возвращает их. **Сетевого запроса нет.**

Этот подход обеспечивает максимальную производительность интерфейса и четкое разделение ответственности между компонентами и хранилищем состояния.

## 11. Продвинутые концепции: Контекстное Окно и Нормализованный Кэш

### Контекстное Окно: показываем данные снаружи

Требование: при "проваливании" на уровень, пользователь должен видеть не только дочерние элементы, но и небольшой контекст "слева" и "справа" для создания ощущения единого потока.

**Реализация:**

Это становится задачей для **бэкенда** и нового, более умного API-запроса. Простого `GET /nodes/{id}/children` уже недостаточно.

1.  **Новый API endpoint:** Мы вводим `GET /api/context/{nodeId}?left=25&right=25`.
    -   `nodeId`: ID узла, в который мы "проваливаемся" (например, `arc-1`).
    -   `left=25`: Сколько узлов показать "слева" (предшествующих).
    -   `right=25`: Сколько узлов показать "справа" (последующих, включая дочерние).

2.  **Логика бэкенда (очень важна):**
    -   **Путь "вправо" (right):** Начиная от `nodeId`, бэкенд начинает обход графа по `NEXT`-связям. Если он встречает `BranchSet`, он должен следовать правилу: **"всегда выбираем первую ветку"** (или ветку, помеченную как `is_main_branch`). Он собирает 25 узлов по этому пути.
    -   **Путь "влево" (left):** Это сложнее. Бэкенд должен идти по **обратным** `NEXT`-связям. Если он доходит до узла, в который входит несколько `NEXT`-связей (слияние), он также должен выбрать один путь (например, первый по `id`).
    -   **Результат:** Бэкенд возвращает **один плоский, упорядоченный массив** из 51 элемента (`25 + 1 (текущий) + 25`), представляющий собой одну, главную, бесшовную временную линию.

3.  **Отображение на клиенте:** `TimelineView` получает этот массив и просто его отображает. Он остается "глупым" и не занимается сложной логикой.

### Решение проблемы кэша: Нормализация

Вопрос: *"Насколько проблемен вопрос повторения данных в кэше?"*

**Ответ: Очень проблемен.** Если один и тот же узел (например, общая сцена) загружен как часть разных запросов, в простом кэше (`Map<parentId, childrenArray>`) появятся его дубликаты. Это приводит к двум проблемам:
1.  **Расход памяти.**
2.  **Рассинхронизация данных:** Если обновить узел в одном месте кэша, его копия в другом месте останется старой, что приведет к багам отображения.

**Правильное решение — Нормализованный кэш.**

В `contentStore` мы используем два хранилища:

1.  `nodes: Map<string, StoryNode>`
    -   **Единый источник правды.** Плоская таблица, где каждый узел хранится **только один раз** по своему `id`.
    -   Пример: `nodes.set('scene-123', { id: 'scene-123', title: 'Погоня' })`.

2.  `contexts: Map<string, string[]>`
    -   Хранит **только ID** узлов для каждого загруженного контекста.
    -   Пример: `contexts.set('context_for_arc-1', ['scene-122', 'scene-123', 'scene-124'])`.

**Как это работает:**

-   Когда `fetchContext('arc-1')` возвращает с бэкенда массив узлов, `contentStore`:
    1.  Пробегается по массиву, и каждый узел добавляет/обновляет в `nodes` (`this.nodes.set(node.id, node)`).
    2.  Создает массив из ID этих узлов.
    3.  Сохраняет этот массив ID в `contexts`.
-   Компонент, который хочет отобразить контекст, использует `getter`, который берет массив ID из `contexts`, а затем для каждого ID подставляет полный объект узла из `nodes`.

**Преимущества:**

-   **Нет дублирования:** Каждый узел существует в памяти в одном экземпляре.
-   **Атомарные обновления:** Чтобы изменить заголовок сцены, нужно обновить его **в одном месте** (`state.nodes.get('scene-123').title = '...';`). Все части интерфейса, использующие этот узел, автоматически обновятся благодаря реактивности Vue.
-   **Консистентность данных** гарантирована.

## 12. Итоговая архитектура API и Кэша

### Ответы на финальные вопросы

**Вопрос 1: Производительность и сложность O(N) на клиенте?**

Сборка итогового списка на клиенте (соединение `contexts` и `nodes`) — **чрезвычайно быстрая операция**. 

-   `this.contexts.get(contextId)` - это `O(1)` (получение массива ID).
-   Далее мы итерируем по этому массиву (размером `M`, например, 51 элемент) и для каждого ID делаем `this.nodes.get(nodeId)`, что также является `O(1)`. 

Итоговая сложность — **O(M)**, где M — количество элементов в **видимом окне**, а не общее количество узлов в проекте. Для окна в ~50 элементов это практически мгновенно.

**Вопрос 2: Лимиты передачи данных.**

Типичные HTTP-серверы (Nginx, Apache) легко обрабатывают запросы/ответы размером в несколько мегабайт. Однако для отзывчивого веб-приложения принято считать хорошей практикой держать размер ответа API в пределах **100-300 КБ**. Наша модель с окном в 50-100 узлов идеально вписывается в эти рамки. Если один узел в JSON-представлении весит 1-2 КБ, то 100 узлов — это 100-200 КБ, что является отличным показателем.

### Итоговая структура API

Для максимальной эффективности и информативности, мы определим следующую структуру.

**API Endpoint:**
`GET /api/context/{nodeId}?window=51`
-   `nodeId`: ID центрального узла нашего окна.
-   `window`: Общее количество узлов, которое мы хотим получить (нечетное число для симметрии).

**Backend Logic:**
Бэкенд находит `nodeId`, а затем идет по `NEXT`-связям "влево" и "вправо" (придерживаясь "магистрального" пути), чтобы собрать `(window - 1) / 2` соседей с каждой стороны. Затем он формирует и возвращает **один плоский массив** узлов.

**API Response Payload (Структура ответа):**
Каждый узел в возвращаемом массиве должен быть "обогащенным":

```json
[
  {
    "id": "scene-123",
    "type": "Scene",
    "title": "Погоня по крышам",
    "content_summary": "Герой преследует злодея...",
    // -- ОБОГАЩЕНИЕ ДАННЫХ --

    // 1. Информация о родителе (ответ на ваш вопрос)
    "parent": {
      "id": "chapter-5",
      "type": "Chapter",
      "title": "Побег из города"
    },

    // 2. Информация о ветвлении (если узел - точка ветвления)
    "branch_info": {
      "is_branch_point": true,
      "branches": [
        { "target_node_id": "scene-124a", "target_node_title": "Спрыгнуть на поезд" },
        { "target_node_id": "scene-124b", "target_node_title": "Свернуть в переулок" }
      ]
    } 
  },
  // ... другие узлы ...
]
```

### Финальная модель кэширования

Наш `contentStore` будет использовать **нормализованный кэш** с этими обогащенными объектами:

1.  `nodes: Map<string, EnrichedStoryNode>`: Хранит полные, обогащенные объекты узлов. **Единый источник правды.**
2.  `contexts: Map<string, string[]>`: Хранит **только ID** для каждого загруженного "окна" (`context_for_node-123_window-51`).

**Преимущества этой итоговой архитектуры:**

-   **Максимально информативно:** Клиент получает всю необходимую информацию (включая родителей) за один запрос, минимизируя задержки.
-   **Производительно:** Размер ответа контролируется параметром `window`, а клиентские операции по сборке данных имеют линейную сложность O(M) от малого числа M.
-   **Надежно:** Нормализованный кэш гарантирует консистентность данных и отсутствие дублирования.
-   **Чистота кода:** Логика на клиенте остается простой: запросил -> положил в кэш -> отобразил. Вся сложность по навигации в графе инкапсулирована на бэкенде.
