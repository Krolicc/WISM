## Сценарий 1: Первичная загрузка / Пользователь открывает корень истории

**Ситуация:** Пользователь впервые заходит в приложение или кликает на самый верхний уровень навигации ("хлебных крошек"), чтобы увидеть общую структуру истории.

### 1. Действие Пользователя

-   Открывает веб-приложение.

### 2. Действия Frontend

1.  Главный компонент приложения монтируется.
2.  Он определяет, какой узел является точкой входа. Обычно это корневой узел истории (например, с `id: 'story-1'`).
3.  Вызывается `action` в `contentStore`, например: `fetchContext('story-1', { window: 51 })`.
4.  Пока данные загружаются, на экране отображается индикатор загрузки (спиннер).

### 3. Действия Backend

1.  Получает запрос: `GET /api/context/story-1?window=51`.
2.  Находит узел `story-1`.
3.  **Отрабатывает логику "Контекстного Окна":**
    -   **"Влево":** Пытается найти предшественников (`predecessors`) для `story-1`. Так как это корень, их нет. Левая часть окна пуста.
    -   **"Вправо":** Находит дочерние узлы `story-1` (например, Арки). Находит самую первую Арку (стартовый узел). От нее начинает обход по `NEXT`-связям по "магистральному пути" (по умолчанию — первая ветка), чтобы собрать `(51 - 1) = 50` узлов.
4.  **Обогащает данные:** Для каждого из 51 узла (сама `story-1` + 50 арок) бэкенд формирует полный JSON-объект, включающий `parent` и `branch_info` (если применимо).
5.  Отправляет ответ: один плоский массив из 51 обогащенного объекта узла.

### 4. Завершающие действия Frontend

1.  `contentStore` получает массив данных.
2.  **Происходит нормализация кэша:**
    -   Store пробегается по всему массиву. Каждый уникальный узел из массива добавляется или обновляется в `state.nodes` (`Map<string, EnrichedStoryNode>`).
    -   Из массива извлекаются только `id` в том же порядке. Этот массив `id` сохраняется в `state.contexts` (`Map<string, string[]>`) под ключом, описывающим запрос (например, `'context_for_story-1_window-51'`).
3.  **Отображение:**
    -   Компонент `TimelineView` через `getter` реактивно получает от `contentStore` готовый к отображению, упорядоченный список узлов (собранный из `contexts` и `nodes`).
    -   Индикатор загрузки скрывается.
    -   На экране появляется таймлайн, показывающий корневой узел истории и следующие за ним 50 арок, образуя единую временную линию.

## Сценарий 2: "Проваливание" вглубь / Пользователь кликает на узел

**Ситуация:** На экране отображается таймлайн (например, список Арк). Пользователь хочет посмотреть содержимое одной из Арк.

### 1. Действие Пользователя

-   Дважды кликает (или совершает другое действие "проваливания") по узлу на таймлайне (например, по `Arc` с ID `arc-3`).

### 2. Действия Frontend

1.  Обработчик события в `TimelineView` фиксирует клик и ID целевого узла (`arc-3`).
2.  Обновляется глобальное состояние навигации (например, в `route` или `navigationStore`), `activeNodeId` становится `arc-3`.
3.  **Проверяется кэш:** `TimelineView` вызывает `action` `contentStore.fetchContext('arc-3', { window: 51 })`.
4.  `fetchContext` сначала проверяет, есть ли в `state.contexts` запись для ключа `'context_for_arc-3_window-51'`.
    -   **Если есть (кэш-хит):** `action` мгновенно возвращает данные, собранные из `state.nodes`. Сетевой запрос не выполняется. Переходим сразу к шагу 4.
    -   **Если нет (кэш-мисс):** `action` выполняет сетевой запрос. На экране отображается спиннер.

### 3. Действия Backend (в случае кэш-мисс)

1.  Получает запрос: `GET /api/context/arc-3?window=51`.
2.  Находит узел `arc-3`.
3.  **Отрабатывает логику "Контекстного Окна":**
    -   **"Влево":** Идет по обратным `NEXT`-связям от `arc-3` и собирает 25 узлов-соседей (другие Арки).
    -   **"Вправо":** Смотрит на дочерние узлы `arc-3` (Главы).
        -   **Исход А (Линейный сюжет):** `arc-3` содержит простую последовательность Глав. Бэкенд находит первую Главу, и от нее собирает по `NEXT`-связям 25 узлов.
        -   **Исход Б (Витиеватый сюжет):** `arc-3` содержит `BranchSet` в самом начале. Бэкенд видит `BranchSet`, помечает саму `arc-3` как точку ветвления (`is_branch_point: true`), а затем для построения пути "вправо" выбирает "магистральную" ветку (например, первую) и собирает 25 узлов уже по ней.
4.  **Обогащает данные:** Формирует для каждого узла полный JSON с `parent` и `branch_info`.
5.  Отправляет ответ: один плоский массив из 51 узла.

### 4. Завершающие действия Frontend

1.  `contentStore` получает данные (либо из кэша, либо из сети).
2.  Если данные пришли из сети, происходит их **нормализация** и сохранение в `state.nodes` и `state.contexts`.
3.  **Отображение:**
    -   `TimelineView` реактивно обновляется, получая новый список узлов из `getter`'а.
    -   Спиннер (если был) скрывается.
    -   На экране появляется новый таймлайн, отцентрированный на `arc-3`. Пользователь видит Арки слева, саму `arc-3` в центре, и ее дочерние Главы справа, что создает ощущение "проваливания" и бесшовного потока.
    -   Обновляются "хлебные крошки" в навигации: `Story > Arc 3`.

## Сценарий 3: Навигация "вверх" / Пользователь использует "хлебные крошки"

**Ситуация:** Пользователь находится глубоко в структуре (например, на уровне Сцены: `Story > Arc 3 > Chapter 5 > Scene 12`), а на экране отображен контекст для `Scene 12`. Он хочет вернуться на уровень `Arc 3`.

### 1. Действие Пользователя

-   Кликает на ссылку "Arc 3" в панели "хлебных крошек".

### 2. Действия Frontend

1.  Обработчик клика в компоненте "хлебных крошек" получает ID целевого родительского узла (`arc-3`).
2.  Обновляется глобальное состояние навигации, `activeNodeId` становится `arc-3`.
3.  **Проверяется кэш:** `TimelineView` (или другой компонент-контейнер) вызывает `action` `contentStore.fetchContext('arc-3', { window: 51 })`.
4.  `fetchContext` проверяет, есть ли в `state.contexts` запись для ключа `'context_for_arc-3_window-51'`.
    -   **Кэш-хит (наиболее вероятный исход):** Так как мы уже "проваливались" в `arc-3` в Сценарии 2, чтобы добраться до `Scene 12`, запись в кэше уже существует. `action` мгновенно возвращает данные, собранные из `state.nodes`. **Сетевой запрос не выполняется.**

### 3. Действия Backend

-   **Не вызываются.** Вся операция происходит на клиенте.

### 4. Завершающие действия Frontend

1.  `contentStore` мгновенно отдает `TimelineView` запрошенный контекст из кэша.
2.  **Отображение:**
    -   `TimelineView` реактивно обновляется, получая список узлов для `arc-3`.
    -   Поскольку нет сетевого запроса, **никаких спиннеров не появляется**. Переключение происходит мгновенно.
    -   На экране снова отображается таймлайн, отцентрированный на `arc-3`, как это было в конце Сценария 2.
    -   "Хлебные крошки" обновляются до: `Story > Arc 3`.

### Вывод по сценарию

Этот сценарий демонстрирует всю мощь нормализованного кэша. Навигация "вверх" по уже посещенным путям становится мгновенной, что создает у пользователя ощущение очень быстрого и отзывчивого интерфейса.

## Сценарий 4: Переключение на альтернативную ветку

**Ситуация:** Пользователь видит таймлайн, где узел "Сцена А" явно помечен как точка ветвления (например, иконкой "..."). Текущий таймлайн показывает "магистральный" путь, идущий после "Сцены А". Пользователь хочет исследовать другой путь.

### 1. Действие Пользователя

1.  Кликает на иконку "..." возле "Сцены А".
2.  Во всплывающем меню UI (сформированном на основе поля `branch_info` из кэша) видит варианты:
    *   "Пойти по пути 'Нападение'" (ведет к `scene-B1`)
    *   "Пойти по пути 'Отступление'" (ведет к `scene-B2`)
3.  Кликает на вариант "Пойти по пути 'Отступление'".

### 2. Действия Frontend

1.  Обработчик клика получает `target_node_id` выбранной ветки: `scene-B2`.
2.  Глобальное состояние навигации обновляется, `activeNodeId` теперь указывает на `scene-B2`.
3.  Вызывается `action` `contentStore.fetchContext('scene-B2', { window: 51 })`.
4.  `fetchContext` проверяет кэш на наличие ключа `'context_for_scene-B2_window-51'`. Это **кэш-мисс**, так как эта ветка еще не просматривалась.
5.  На экране отображается спиннер.

### 3. Действия Backend

1.  Получает запрос: `GET /api/context/scene-B2?window=51`.
2.  Находит узел `scene-B2`.
3.  **Отрабатывает логику "Контекстного Окна" для `scene-B2`:**
    -   **"Влево":** Идет по обратным `NEXT`-связям. Находит узел-развилку (`BranchSet`), затем `Сцену А`, и от нее продолжает собирать узлы "влево", пока не наберет 25 штук.
    -   **"Вправо":** Идет по `NEXT`-связям *вперед* от `scene-B2`, собирая 25 узлов по этой новой, альтернативной временной линии.
4.  **Обогащает данные:** Формирует для каждого узла в собранном окне полный JSON с `parent` и `branch_info`.
5.  Отправляет ответ: один плоский массив из 51 узла, представляющий собой контекст для новой, выбранной ветки.

### 4. Завершающие действия Frontend

1.  `contentStore` получает новый массив данных.
2.  **Происходит нормализация:**
    -   Новые узлы добавляются в `state.nodes`. Существующие (например, "Сцена А") - обновляются, если это необходимо.
    -   Новый массив ID сохраняется в `state.contexts` под ключом `'context_for_scene-B2_window-51'`.
3.  **Отображение:**
    -   `TimelineView` реактивно обновляется, получая новый список узлов.
    -   Спиннер скрывается.
    -   Таймлайн на экране "переключается". Теперь он показывает совершенно другую последовательность событий, которая начинается после "Сцены А" и идет по пути "Отступления".

### Вывод по сценарию

Этот сценарий показывает, как система элегантно обрабатывает исследование нелинейного сюжета:
-   **Интерактивность:** API заранее сообщает UI о наличии веток (`branch_info`).
-   **Ленивая загрузка:** Неисследованные пути не загружаются, пока пользователь явно не захочет их увидеть.
-   **Универсальность:** Один и тот же API-endpoint (`/api/context/{id}`) и клиентская логика (`fetchContext`) используются для навигации по любой части графа.
-   **Производительность:** Новые данные запрашиваются только при реальной необходимости, а уже загруженные ветки будут в дальнейшем открываться из кэша мгновенно.

## 5. Итоговый граф: Карта Цели

Этот граф представляет собой визуализацию сложной структуры, к которой мы стремимся. Он объединяет все обсуждаемые концепции.

**Легенда:**
- `[NODE_TYPE: id]` - Узел
- `  + (CONTAINS)` - Связь вложенности (иерархия)
- `----(NEXT)---->` - Связь последовательности (повествование)

```
// --- Уровень Истории --- 
[STORY: S1]
  + (CONTAINS)
  |
  +--> [ARC: A1] ----(NEXT)----> [ARC: A2] ----(NEXT)----> [BS: BSA1] // BS = BranchSet
  |                                                        (Ветвление на уровне Арк)
  |                                                          + (CONTAINS)
  |                                                          |--> [ARC: A3] // Начало ветки 1
  |                                                          + (CONTAINS)
  |                                                          |--> [ARC: A4] // Начало ветки 2
  |                                                                 
  + (CONTAINS) ... (все остальные узлы, включая ARC A5)

// Логика связей, которая определяет граф:
// [ARC: A2] ----(NEXT)----> [BS: BSA1]
// [ARC: A3] ----(NEXT)----> [ARC: A5]
// [ARC: A4] ----(NEXT)----> [ARC: A5]
// Результат: A2 ведет к выбору между A3 и A4, и обе эти ветки затем сливаются в A5.


// --- Детализация ARC A3: параллельные и ветвящиеся главы --- 

[ARC: A3]
  + (CONTAINS)
  |
  +--> [CHAPTER: C1] ----(NEXT)----> [CHAPTER: C2] // Простая последовательность
  |
  + (CONTAINS)
  |
  +--> [CHAPTER: C3] // Параллельная, независимая глава, не связанная с C1/C2
  |
  + (CONTAINS)
  |
  +--> [CHAPTER: C4] ----(NEXT)----> [BS: BSC4]
                                         (Ветвление, ведущее к C5 и C6)
                                           + (CONTAINS) --> [CHAPTER: C5]
                                           + (CONTAINS) --> [CHAPTER: C6]


// --- Детализация CHAPTER C5: сложная структура сцен --- 

[CHAPTER: C5]
  + (CONTAINS)
  |
  +--> [SCENE: S5.1] ----(NEXT)----> [BS: BSS5]
  |                                  (Ветвление на Сцены A и B)
  |                                    + (CONTAINS) --> [SCENE: S5.A]
  |                                    + (CONTAINS) --> [SCENE: S5.B]
  |                                                          
  + (CONTAINS)
  |
  +--> [SCENE: S5.C] // Узел слияния для S5.A и S5.B
  |
  + (CONTAINS)
  |
  +--> [SCENE: S5.D] // Независимая сцена в той же главе

// Логика связей для Сцен:
// [SCENE: S5.A] ----(NEXT)----> [SCENE: S5.C]
// [SCENE: S5.B] ----(NEXT)----> [SCENE: S5.C]
// Результат: S5.1 ведет к выбору между A и B, которые затем сливаются в С. 
// Сцена S5.D существует параллельно и независимо.
```

1. Новая структура Branches:

Это — сердце вашей идеи. Вместо того чтобы просто хранить узлы, мы создаем "карту дорог" всей истории.

Branches — это Map, где ключ — это ID точки ветвления (branchSet), а значение...
...это еще один Map, где ключ — это ID возможного выбора (например, arc-2-main), а значение...
...это линейный список (массив) ID узлов, который представляет собой полный, заранее просчитанный путь от этой точки до следующей развилки или до конца.
Пример на основе нашего JSON:

Branches: Map {
  "bs-arc-1" => Map {
    "arc-2-main" => ["arc-2-main", "chapter-2-1"], // Путь 1: от выбора до конца
    "arc-2-alt"  => ["arc-2-alt", "chapter-2-alt-1"]  // Путь 2: от выбора до конца
  }
}


2. Дополнительные поля в узлах Branches:

Эти поля — метаданные, которые делают "карту дорог" умной:

Логический Конец (is_leaf: true): Мы точно знаем, что этот путь — тупик. UI может перестать рисовать стрелку "дальше".
Продолжение (continuation_id: string): Для очень длинных линейных глав. Мы можем разбить список на части (для пагинации) и всегда знать, какой список загружать следующим.
Ветка (next_branch_set_id: string): Самое важное. Список заканчивается не тупиком, а новой развилкой. UI знает, что нужно снова рендерить компонент выбора, но уже для next_branch_set_id.
Обобщение / Слияние (merge_point_id: string): Ключ к нелинейности! Два или более разных списка могут в конце ссылаться на один и тот же merge_point_id. Система будет знать, что ветки сошлись, и продолжит путь с этой общей точки.

Это абсолютно верный и очень глубокий вывод. Вы предлагаете сделать сложную работу один раз — при первоначальной загрузке и парсинге истории. Мы проходим по всему графу узлов и "компилируем" его в простые, линейные массивы.

А во время работы приложения (в UI) мы просто итерируемся по готовым спискам. Это на несколько порядков проще и производительнее, чем рекурсивно обходить дерево на каждый клик.

Производительность: UI будет работать молниеносно. Вместо сложных вычислений — простая итерация по массиву.
Предсказуемость: Логика UI становится тривиальной. Он получает список и рендерит его. Если в конце списка есть next_branch_set_id — рендерит выбор. Всё.
Управление состоянием: Выбор игрока — это просто выбор нужного списка из Branches. Сохранить прогресс — значит сохранить последовательность выбранных ключей.
Решение проблемы с кэшем: Теперь это решается элегантно. При изменении структуры истории (через commitActions) мы просто заново запускаем наш парсер, который перестраивает Branches на основе обновленного списка Nodes. Сложность инкапсулирована в одном месте.
Это гораздо более сложный в первоначальной реализации, но несравнимо более мощный, масштабируемый и правильный путь. Он закладывает фундамент для сложного нелинейного повествования.
